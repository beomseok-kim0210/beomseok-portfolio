## 어떤 모델을 얼마나 세게 돌릴지, 그리고 모델에게 코드가 '누구 것'이라고 말할지 — 앤트로픽이 숫자로 답한 두 가지

### 앤트로픽 공식 모델 선택 가이드 — Opus 5.5 medium에서 시작해 모델보다 추론 강도를 먼저 조절하고, 긴 파일·로그 읽기는 Haiku 서브에이전트에 넘겨 메인 컨텍스트를 가볍게 유지한다

앤트로픽이 11월 9일 개발자 사이트 claude.dev에 "Which Claude model should you build with?" 가이드를 올렸고, choi.openai가 13개 연속분으로 정리했다. [어제 팁 노트](ai-tips-2026-11-10.md)가 Fable 5.2 발표문에 딸린 권고를 다뤘다면, 이 가이드는 네 모델 전체를 놓고 숫자와 함께 정리한 후속편이다. 겹치는 내용(Fable은 high부터, max는 비권장)은 빼고 새로 나온 것만 추렸다.

**1. 출발점과 오르내리는 기준**
- 기본은 **Opus 5.5 + medium**. Claude Code의 기본 모델이고 토큰 가격이 Fable 5.2의 절반이다.
- 내리는 경우: 버그 수정·명세가 분명한 기능 개발 → Sonnet 5.5 / 분류·라우팅·추출 같은 대량 작업과 서브에이전트 잔업 → Haiku 5.5 / 대화형 세션 → Sonnet 5.5 low~medium.
- 올리는 경우: 대형 리팩터링·아키텍처 설계·깊은 리서치 → Fable 5.2. 명세가 분명해도 마이그레이션·성능 최적화는 Opus 5.5로 하라고 따로 적었다.
- 가격(100만 토큰당 입력·출력): Haiku 5.5 0.1·0.5달러, Sonnet 5.5 2·10달러, Opus 5.5 4·20달러, Fable 5.2 8·40달러. **캐시 읽기는 Opus와 Fable이 똑같이 0.2달러**라, 캐시를 많이 타는 긴 작업에서는 두 모델의 차이가 캐시 밖 입력과 출력에서만 난다. Haiku 5.5는 프롬프트가 10만 토큰을 넘으면 단가가 5배로 뛴다.

**2. 모델을 바꾸기 전에 추론 강도부터**
- SWE-bench Pro에서 Opus 5.5는 high 대비 medium이 2.5점 낮고 비용 70%, low는 8점 낮고 비용 3분의 1, xhigh는 1.4점 높고 비용 2.5배였다. 강도를 올려도 모델에 없는 지식이 생기지는 않는다.
- high를 넘어 한 단계 더 올리면 큰 모델로 바꾸는 만큼 비용이 들 수 있다. 그 구간에서는 **한 단계 위 모델을 더 낮은 강도로** 시험하라는 게 가이드의 권고다.
- 모델이 일을 못 해낼 때 순서: ① 테스트·빌드·엔드포인트 호출 스크립트처럼 스스로 결과를 확인할 수단을 준다 → ② 강도를 한 단계 올린다 → ③ 한 단계 위 모델로 바꾸되 쓰던 강도보다 낮게 시작한다.
- 자동 채점이 가능한 일은 전부 low로 돌리고 실패한 것만 high로 다시 돌리는 방법도 있다. Opus 5.5로 이렇게 했더니 약 97%를 과제당 약 0.17달러에 통과했고, 전부 high는 95.3%에 0.29달러였다.

**3. 컨텍스트도 비용 — 읽는 일은 싼 서브에이전트에게**
- Opus 5.5 기준 컨텍스트가 15만 토큰이면 한 턴의 캐시 읽기가 약 0.03달러, 2만 토큰이면 약 0.004달러다. 수백 턴을 도는 에이전트라면 이 차이가 그대로 쌓인다.
- Claude Code에서는 서브에이전트 정의에 `model: haiku`나 `model: sonnet` 한 줄을 넣으면 된다. 서브에이전트는 자기 컨텍스트에서 일하고 요약만 넘기며, 비용은 그 모델 단가로 청구된다.
- 맡길 일은 파일 찾기·테스트 실행·로그 읽기처럼 **실수해도 금방 드러나는 일**만. 코드 수정과 판단은 메인 모델에 남긴다. 작은 모델이 검색 결과를 잘못 읽으면 메인 모델이 엉뚱한 파일을 열어 토큰을 쓰기 때문이다.
- 기본 Explore 서브에이전트가 이제 세션 모델로 돌아가므로, Explore라는 이름의 haiku 서브에이전트를 직접 만들어 두라는 팁이 있다.

**4. 모델을 섞어 쓸 때 깨지는 지점**
- 프롬프트 캐시는 만든 모델에만 붙는다. 세션 도중 모델을 바꾸면 첫 턴에 대화 전체의 캐시 쓰기 비용을 낸다 → `/compact`로 줄이거나 짧은 계획만 들고 새 세션을 연다. 작은 모델로 내려가면 앞 모델의 추론 기록도 버려진다.
- API에서 모델 이름만 바꾸면 나는 오류: Opus 5.5·Fable 5.2는 thinking을 끄면 오류 / Sonnet·Opus·Fable은 `tool_choice`를 `any`·`tool`로 강제하면 400(→ `auto`에 `strict: true`를 걸고 언제 쓸지 프롬프트에 적는다) / Haiku 4.5→5.5는 `temperature`·`top_p`·`top_k`를 기본값 외로 두면 400 / Fable 5.2는 thinking 블록 앞 기록을 고치면 400.
- 여러 모델을 함께 쓰는 시스템이면 가장 까다로운 모델에 맞춰 요청을 짜 두라고 했다.

**5. 결국 내 작업으로 잰다**
- 실제 과제를 뽑아 테스트 통과 같은 기준을 붙이고, 후보 모델마다 강도 2~3개를 캐시가 섞이지 않게 따로 돌려 점수·비용을 한 그래프에 찍는다. 가장 어려운 과제의 비용을 꼭 따진다(한 검색 벤치마크에서는 20문제 중 2문제가 전체 비용의 43%였다).
- Claude Code라면 `/model`로 두 모델에 같은 일을 맡기고 `/usage`를 비교하면 된다.

> 🔧 **적용 포인트** — 이 포트폴리오 작업 기준으로 옮기면: 평소 UI 수정·버그 수정은 Sonnet 5.5나 Opus 5.5 medium, 셰이더·스크롤 타임라인을 여러 파일에 걸쳐 고치는 리팩터링과 성능 최적화는 Opus 5.5 high, 그래도 막히면 xhigh로 올리기 전에 Fable 5.2 high를 먼저 써 본다.
> `.claude/agents/`에 `model: haiku`를 넣은 Explore 서브에이전트를 하나 만들어 두자. 3D 씬 관련 파일 탐색이나 빌드 로그 읽기가 메인 컨텍스트를 부풀리는 주범이라 효과가 바로 보인다.
> 세션 중간에 `/model`로 바꾸기 전에 `/compact`를 먼저 하는 습관을 들인다. 도슨트 API 코드에서 `tool_choice`를 강제하고 있다면 Sonnet 5.5 이상으로 올릴 때 400이 날 수 있으니 미리 확인한다.

### Fable 5.2 '코드 소유권' 한 문장 — "이 코드베이스는 네 것"이라고 적으면 중복 코드 정리가 10% 미만→약 50%, 대신 출력 토큰 1.5배에 요청 안 한 변경이 섞인다

choi.openai가 앤트로픽 공식 문서 "Prompting Claude Fable 5.2"의 'Say who owns the code' 절을 소개했다. 원문을 직접 확인해 보니 스레드에 빠진 부작용 수치가 함께 적혀 있어 같이 옮긴다.

**무슨 현상인가**
- Fable 5.2는 프롬프트가 코드의 주인을 어떻게 말하느냐에 민감하다. 소유권 언급이 없거나 남의 코드처럼 제시되면, 중복이 생기더라도 **기존 구조에 덧붙이기만** 하고 주변 문제는 고치지 않고 보고만 하는 경향이 있었다.
- 시스템 프롬프트에 이 한 문장을 넣으면 달라진다: `This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it.`
- 앤트로픽의 소규모 코딩 과제 시험에서 이 문장이 있으면 약 절반의 시도에서 중복 코드를 합쳤고, 없으면 10분의 1 미만이었다. 긴 시스템 프롬프트 안에 넣어도 효과가 유지됐고, 요청한 기능 자체는 어느 쪽이든 거의 항상 동작했다.

**공짜가 아니다 — 문서에 적힌 비용**
- 출력 토큰이 약 **1.5배** 늘었고, 아무도 요청하지 않은 변경이 여럿 생겼다(상당수는 새 테스트와 문서).
- 버그 수정 외에 **기존 기능의 동작을 바꾼 경우가 6~10번 중 1번** 있었고, 추론 강도가 높을수록 잦았다.
- 마무리 요약은 큰 변경은 언급하지만 작은 변경은 자주 빠뜨렸다. 문서의 결론은 "요약만 보지 말고 diff를 검토하라"다.
- 사용자가 코드 주인이고 최소한의 변경을 원하는 경우엔 이 문장을 빼라고 했다. 같은 프롬프트에 "지나가는 김에 하는 리팩터링 금지" 같은 범위 제한 규칙을 둬도 소유권 문장의 효과가 상쇄되지 않았다는 점도 주의할 대목이다.

> 🔧 **적용 포인트** — 상시 켜 둘 문장이 아니라 **정리 전용 세션에서만** 쓰는 스위치로 보는 게 맞다. 예컨대 perf 작업처럼 비슷한 훅·유틸이 여러 섹션에 중복된 구간을 정리할 때 세션 첫 메시지에 이 문장을 넣고, 끝나면 요약이 아니라 `git diff`로 동작이 바뀐 곳이 없는지 확인한다.
> 운영 배포 직전의 작은 수정이나 뉴스 노트처럼 범위가 고정된 작업에는 넣지 않는다. CLAUDE.md에 상시로 넣으면 "건드리지 말라"는 다른 규칙과 충돌해도 정리가 일어날 수 있다는 게 문서의 경고다.
