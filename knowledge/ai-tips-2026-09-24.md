## AI에게 성능 최적화를 맡기려면 먼저 "흔들리지 않는 측정"을 쥐여줘야 한다

### 앤트로픽이 claude.ai를 2주 만에 3배 빠르게 만든 방법 — "측정하면 다룰 수 있다", 결정론적 벤치마크와 Claude 상시 투입으로 3,000개 변경·사고 0건

Threads(boris_cherny)는 최근 claude.ai와 데스크톱 앱이 눈에 띄게 빨라진 비결을 담은 claude.dev 블로그 글을 소개하며 "자기 앱을 빠르게 만들려는 엔지니어에게 쓸 만한 교훈이 많다"고 추천했다. 원문(9월 23일 게시)과 웹서치로 확인한 Help Net Security·iPhone in Canada 보도를 종합하면, 팀은 8월 2주 스프린트 동안 3,000개가 넘는 변경을 배포해 13개 지표의 기하평균 기준 3.1배 속도 향상을 얻었고, 그 과정에서 고객에게 드러난 장애나 긴급 롤백은 한 건도 없었다.

**1) 먼저 측정 대상을 좁혔다.** 전체 사용의 95%를 차지하는 네 가지 사용자 동선(앱 실행, 새 대화 시작, 기존 대화 불러오기, 메시지 전송)을 웹·데스크톱별 13개 지표로 쪼갰다. 각 지표는 "사용자 입력 시점부터 결과가 화면에 그려진 시점까지"로 정의하고 클라이언트/서버 구간을 분리했다. 결과적으로 웹 첫 로딩(p75)은 3.1초→0.55초, 기존 대화 로딩은 1.56초→0.65초, 클라우드 세션 메시지 전송은 928ms→48ms로 줄었다.

**2) 노이즈 많은 실측 대신 결정론적 벤치마크를 만들었다.** 벽시계 시간은 매번 흔들리므로, Claude가 오르막을 오를(hill-climb) 수 있는 고정된 지표를 따로 만들었다. `node --predictable` + Valgrind로 순수 JS 핫패스의 명령어 수를 세고, V8 커버리지로 함수 호출 횟수를, React 커밋 수와 훅 개수를, DOM 스타일 재계산·레이아웃 이동·변경 횟수를 측정했다. 헤드리스 Chrome을 120Hz로 고정해 8.33ms 프레임 예산을 재현하기도 했다. 중요한 건 이 지표가 실제 체감 속도와 연결된다는 걸 Claude가 증명하게 한 점이다. 예컨대 메시지 트리 조립의 명령어 수를 48% 줄이자 실제 시간은 78% 줄었다.

**3) Claude를 슬랙 채널에 상시 배치했다.** 내부 모델을 전용 채널에 두고 배포 모니터링, 텔레메트리 점검, 대시보드 관리, 개선안 구현과 제안을 상시 지시로 맡겼다. 150개가 넘는 스레드를 비동기로 병렬 운영했으며, 공개된 중간 지시문도 인상적이다. Claude의 보수적인 추정에는 "더 과감해져도 된다"고, 방향을 틀 땐 "아직 안 건드린 것, 오르막을 오를 수 있는 곳, 가장 기회가 큰 곳을 다시 훑어보자. 황당한 아이디어도 환영한다"고, 지표를 늘릴 땐 "이 지표를 개선하면 실제 벽시계 시간이 줄어든다는 걸 증명하라"고 요구했다.

**4) 안전장치를 겹겹이 뒀다.** 최적화 전에 단위 테스트를 먼저 깔고, 자동 리뷰에 사람 승인을 필수로 붙였다. 기능 플래그를 약 200개 만들어(킬 스위치/점진 확대로 구분) 스프린트 종료 시점엔 절반 이상을 제거했고, 고위험 변경은 직원 → 1% → 전체 순으로 풀었다. 입력창은 jsdom 렌더링 결과를 14개 뷰포트에서 ±1px 오차로 대조했고, 레이아웃 이동은 0.1px 단위로 수집해 0이 아니면 바로 조사 스레드를 열었다.

**5) 실제로 효과가 컸던 기법들.** React가 뜨기 전에 정적 HTML 입력창을 먼저 심어 바로 타이핑할 수 있게 했고(입력 가능 시점 2.93초→0.36초), 데스크톱 셸엔 V8 코드 캐시를 미리 컴파일해 넣었다. 대화 전환 시 입력창을 언마운트하지 않고 유지해 사이드바 재렌더를 90% 줄였고, 마우스를 올리면 세션을 미리 불러왔다. `:root:has()` 선택자 하나가 모든 DOM 변경마다 24ms를 더하고 있던 걸 찾아 지웠고, 코드 하이라이팅에서 em dash 때문에 문자열이 UTF-16으로 부풀던 문제를 20줄로 고쳐 첫 코드 블록 처리 시간을 1.0초→0.35초로 줄였다. 남아 있던 `location.reload()` 하나가 하루 50만 번의 보이지 않는 새로고침을 일으키던 것도 잡았다. 스트리밍 중엔 완성된 코드 블록을 메모이즈해 청크마다 메시지 전체 길이만큼 다시 계산하던 작업을 없애고, 자라나는 코드 펜스의 토큰화는 워커 스레드로 옮겼다. 그 결과 긴 응답의 총 블로킹 시간이 750ms→200ms, CPU 사용량은 67% 줄었다.

팀이 정리한 한 줄 교훈은 "Claude와 함께라면, 측정하는 순간 그 문제는 다룰 수 있는 문제가 된다"이다. 성능 최적화가 막연한 감각의 영역이던 이유는 대부분 측정이 흔들리기 때문이었고, 흔들리지 않는 측정을 먼저 만들어주면 AI가 수천 번의 작은 개선을 안전하게 반복할 수 있다는 것이다.

> 🔧 **적용 포인트** — 포트폴리오(Next.js + R3F + GSAP + Lenis)에서 바로 가져올 만한 것: ① 도슨트·크라임씬 진입처럼 핵심 동선 3~4개만 골라 "입력→화면 반영" 지표를 정의하고, Claude Code에게 먼저 결정론적 벤치마크(React 커밋 수, 스타일 재계산 횟수, 레이아웃 이동)를 만들게 한 뒤 최적화를 맡길 것. ② `globals.css`에서 `:has()` 선택자, 특히 `:root`/`body`에 걸린 것을 찾아볼 것 — DOM 변경마다 전체 스타일을 다시 계산시킬 수 있다. ③ 도슨트 채팅 스트리밍은 완성된 메시지·코드 블록을 memo로 고정하고, 채팅 패널을 닫았다 열 때 언마운트하지 않는 방식을 검토할 것. ④ Lenis·GSAP 스크롤 구간은 헤드리스 Chrome 120Hz 프레임 스텝 테스트 아이디어를 참고해 프레임 예산(8.33ms/16.6ms) 초과 여부를 수치로 확인할 것.
