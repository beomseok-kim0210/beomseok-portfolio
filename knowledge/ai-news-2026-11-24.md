## PR 마무리를 에이전트에게 넘기는 Claude Ship, 패치 전 공백을 에이전트가 메우는 Shirudo, 그리고 기억을 모델 안으로 넣은 MemT

### 앤트로픽 Claude Ship — /ship 한 번으로 커밋·PR·리뷰·수정 감시까지 이어 주고, 저장소 단위로 켜면 Code Review·PR Steward·Claude Approvals가 팀 PR을 맡는다(Team·Enterprise 베타, 네이티브 Windows에선 감시가 시작되지 않음)

앤트로픽이 11월 23일 GitHub PR을 다루는 에이전트 묶음 **Claude Ship**을 공개했다. testingcatalog는 "Claude가 PR을 스스로 리뷰·수정·승인한다"고 요약했는데, 공식 문서를 보면 구성은 세 개다.

- **Code Review**: 이슈를 인라인 코멘트로 남긴다(10월에 GA된 그 기능).
- **PR Steward**: 실패한 체크·충돌·리뷰 코멘트를 보고 수정 커밋을 푸시한다. 승인이나 병합은 하지 않는다. Claude GitHub App으로 돌고, 초안·포크·봇이 연 PR은 기본으로 건너뛰며 `@claude stop`으로 멈춘다.
- **Claude Approvals**: 저장소의 `.claude/approvals.yml` 정책에 따라 "누가 더 승인해야 하는지"를 체크로 보고한다. 규칙마다 경로와 판정(approves·comments·blocks)을 적고, 모든 변경 파일이 규칙으로 덮이고 해당 규칙이 전부 approves일 때만 Claude가 승인한다. `.gitattributes`·심볼릭 링크·서브모듈 포인터를 건드리는 변경은 절대 승인하지 않고, 정책 파일은 기본 브랜치에서만 읽는다. observe 모드로 먼저 돌려 볼 수 있다.

개발자가 직접 쓰는 입구는 CLI 명령 `/ship`이다. ① 필요하면 커밋·푸시하고 내 이름으로 PR을 연 뒤 ② `/code-review`로 리뷰하고 ③ 체크·충돌·코멘트에 맞춰 수정을 푸시하는 '감시'를 시작하며 ④ 병합은 사람이 한다. 이미 열린 PR에는 `/steward`로 ①②를 건너뛰고 감시만 붙인다. 확인 프롬프트 없이 바로 움직이고, 감시는 PR당 최대 7일이며 세션이 열려 있어야 한다. 요구 사항은 Claude Code v2.1.330 이상, GitHub CLI 2.63 이상, git 2.38 이상이다. 조직 관리자는 Organization settings에서 저장소 전체에 켤 수 있어 개발자가 `/ship`을 치지 않아도 팀 PR에 돌게 된다.

제약도 분명하다. 대상은 Team·Enterprise 플랜의 GitHub 프로젝트이고(공식 문서에 Pro·Max 언급은 없음), Zero Data Retention·HIPAA 구성·고객 관리 키를 쓰는 조직은 쓸 수 없다. 에이전트 비용은 플랜 사용량과 별도로 조직 사용 크레딧에서 토큰 단위로 빠지며, PR Steward는 관리자가 한도를 정하기 전까지 지출 상한이 없다. The New Stack 등은 "승인 정책 파일이 무엇이 병합되는지를 정한다"는 점을 핵심으로 짚었다 — 정책을 느슨하게 쓰면 사람 승인 없이 병합되는 경로가 생길 수 있다는 뜻이다.

> 🔧 **적용 포인트** — 이 포트폴리오는 master 푸시가 곧 Vercel 운영 배포라서, `/ship`을 쓰더라도 master 직행이 아니라 브랜치→PR 흐름에서만 쓰는 게 맞다. 문서상 **네이티브 Windows에서는 감시(watch)가 시작되지 않으므로**, 지금 PC에서는 커밋·PR·리뷰까지만 기대하고 체크 수정 루프는 WSL에서 돌리는 걸 전제로 시험해 보자. Approvals를 붙인다면 `knowledge/ai-news-*.md`처럼 콘텐츠만 바뀌는 경로만 approves로 열고, `src/`·설정 파일은 comments로 두는 식의 좁은 정책부터 시작하는 게 안전하다.

### 오픈AI·시스코 Shirudo — 패치가 나오기 전까지 에이전트가 취약한 경로만 막는 방패를 짜서 재시작 없이 붙이는 BSD 2-Clause 오픈소스 리눅스 런타임, Codex가 만든 방패가 돌아가는 Elasticsearch에서 Java4Shell 공격을 막았다

오픈AI와 시스코가 11월 23일 리눅스 런타임 **Shirudo**(일본어 '방패')를 공개했다. 패치를 시험·배포하는 데 며칠에서 몇 주가 걸리는 사이, AI 에이전트가 운영체제 안에서 도는 작은 프로그램을 직접 짜서 **취약한 동작 하나만** 막는 임시 방패를 서버 재시작 없이 붙이는 도구다. 바탕은 커널을 고치지 않고 정해진 지점에서 검증된 작은 프로그램을 돌리게 해 주는 eBPF이고, 시스코 산하 Isovalent의 보안 도구 Tetragon을 에이전트용으로 다시 쓴 것이다. 사람용 정책 언어 대신 에이전트가 잘하는 '코드'로 방어를 짜게 했다는 게 설계 의도다.

시험 대상은 [11/18에 다룬 Java4Shell(CVE-2026-114938)](ai-news-2026-11-18.md)이다. 오라클 패치가 나온 다음 날 시스코 팀이 취약점 정보를 Codex 기반 제어 루프에 넣자, Codex가 Base64 입력을 검사하는 방패를 만들었고 이를 실행 중인 Elasticsearch 9.5.5에 붙여 공격을 시도하자 'Base64 guard rejected candidate' 로그와 함께 차단됐다. 서비스는 계속 돌았다. 다만 Isovalent 설명으로는 이 방패가 eBPF 프로그램이 아니라 애플리케이션에 주입한 **Java 바이트코드**였다 — "eBPF 방패"라는 요약과는 결이 조금 다르다.

에이전트가 쓴 코드를 커널 근처에 넣는 만큼 신뢰 장치를 겹겹이 뒀다. 방패는 운영자 컴퓨터에서 서명된 패키지로 만들어지고, 대상 서버는 봉인된 키링으로 서명을 확인한 뒤에만 불러오며 서명 없는 BPF 프로그램은 거부한다. 서명 키가 운영자 컴퓨터를 떠나지 않아 대상 서버의 root로도 상태를 바꿀 수 없고, 방패 적재·해제는 TPM에 기록된다. 각 방패는 실제 공격과 실제 부하로 시험한 뒤 운영자가 승인해야 배포된다. 저장소에는 주요 코드를 Lean 4·CBMC로 증명한 파일, 퍼징 테스트, 위협 모델 문서도 함께 올라왔다. 라이선스는 BSD 2-Clause(BPF 프로그램은 BSD/GPL 이중)이고 아직 정식 릴리스 전 단계다.

맥락상 오픈AI는 이번 달 리눅스 취약점 948건 보고, GPT-6 Cyber 출시에 이어 '찾기'에서 '막기'까지 보안 발표를 이어 가고 있고, 앞으로 취약점 공개 때 시험을 마친 방패를 함께 내겠다고 밝혔다. choi.openai는 구글 맨디언트 집계로 취약점 악용까지 걸리는 평균 기간이 2018년 63일에서 2025년 -7일(패치보다 공격이 먼저)이 됐다는 점을 배경으로 들면서, 방패를 짜는 두뇌가 결국 비공개 프런티어 모델이라 "최신 모델에 먼저 닿은 곳부터 먼저 패치되는" 격차가 생길 수 있다고 짚었다. 반대로 냉정하게 보면 공개된 근거는 통제된 Elasticsearch 시험 하나뿐이고 차단율·오탐률·오버헤드 수치나 독립 평가는 아직 없다(StartupHub 등 지적).

### MemTensor MemT-1.0-Pro — 과거 대화를 외부 DB 대신 모델 내부 메모리에 압축해 두는 '메모리 네이티브' 모델의 최상위판, 엔비디아 Nemotron 3 Ultra 기반 약 565B

대부분의 AI 기억 기능은 과거 대화를 외부 DB에 넣어 두고 필요할 때 검색해 프롬프트에 붙이는 RAG 방식이다. MemOS를 만든 MemTensor의 **MemT-1.0** 계열은 반대로 Transformer 내부의 별도 메모리 구조(Gated DeltaNet-2 기반 갱신 + 메모리 용량과 학습 파라미터를 함께 키우는 Mixture-of-Storage)에 과거 정보를 압축해 두고, 이후엔 원본 대화를 다시 넣지 않고 그 기억을 쓴다. 메모리 크기는 대화가 길어져도 일정하다. 대신 모든 대화를 원문 그대로 기억하지는 않는다.

10월에 Nano(Qwen3.6-35B-A3B 기반)·Flash(DeepSeek-V4-Flash 기반)가 먼저 나왔고, 이번 **Pro**는 엔비디아 Nemotron-3-Ultra-550B-A55B를 바탕으로 풀 어텐션 레이어 12개에 메모리 모듈을 붙인 약 565B 모델이다. 기술 보고서 기준 메모리 벤치마크 평균 53.08로 비교 대상 파라메트릭 메모리 방식 중 1위이고, Nano 기준으로는 128K 토큰 이력에서 전체 KV 캐시 대비 추론 약 1.86배 빠르고 저장 공간은 66분의 1이라고 한다. 가중치는 허깅페이스에 있지만 `trust_remote_code=True`가 필요하고, 보고서 라이선스는 CC BY-NC-SA 4.0(비상업)으로 표기돼 있어 모델 카드 확인이 필요하다.

원문 댓글에서는 "내부 압축 메모리는 검색 지연은 줄지만, 특정 기억만 골라 지우거나 왜 이 답이 나왔는지 감사 추적을 남기기 어렵다 — 당분간 개인 비서는 내부 메모리, 기업 시스템은 외부 DB로 나뉠 것"이라는 반응이 나왔다. 기억을 지우고 출처를 보여 줘야 하는 서비스라면 RAG가 여전히 유리하다는 지적이다.

> 🔧 **적용 포인트** — 도슨트(/docent)의 하이브리드 RAG는 답변 근거를 큐레이션 코퍼스에서 바로 보여 줄 수 있다는 게 장점이라, 지금 구조를 바꿀 이유는 없다. 면접에서 "왜 RAG냐"는 질문이 나오면 '내부 메모리 모델은 삭제·출처 추적이 어렵고, 공개 포트폴리오 안내원은 근거 노출과 내용 수정이 더 중요하다'는 비교 논거로 쓸 만하다.
