지난주(10/12~10/16) 앤트로픽이 낸 발표 중 아직 다루지 않은 네 가지를 묶었다. 두 가지는 매일 쓰는 Claude Code와 API에 바로 닿는 변화다. 나머지 둘은 모델 보호 정책과 AI 연구 능력에 관한 소식이다.

### Claude Code 데스크톱 다중 세션 개편 — 병렬 작업은 중첩 세션으로, 곁가지 질문은 /btw 탭으로, 사이드바는 '내 차례인 세션'을 따로 모은다

btibor91의 주간 정리에 따르면 Claude Code 데스크톱이 여러 세션을 나란히 돌리는 방식에 맞춰 다시 짜였다. 4월 개편에서 한 창에 여러 세션과 사이드바를 들였는데, 10월 14일(UTC) 업데이트는 그 흐름을 더 다듬었다. 확인된 내용은 다음과 같다.

- **저장된 환경**: 폴더 여러 개, SSH 호스트, 클라우드를 하나의 '환경'으로 저장한다. 폴더마다 Git worktree를 선택적으로 붙일 수 있고, 기본 위치는 `<프로젝트 루트>/.claude/worktrees/`다. 새 세션 화면에서 최근 폴더를 한 번에 연다.
- **중첩 세션**: Claude가 작업을 병렬로 나누면 각 작업이 하위 세션이 되고, 결과만 메인 스레드로 보고한다. Claude가 제안한 후속 작업은 칩 하나를 눌러 별도 세션으로 띄운다.
- **/btw 곁가지 질문**: 별도 탭에서 열리고 메인 세션 기록에 섞이지 않는다(단축키 Cmd+;).
- **사이드바**: 일하는 중인 세션과 내 입력이 필요한 세션을 나눠 보여준다. 세션 안에는 실시간 할 일 목록, 내 차례가 됐을 때의 요약 카드, 실행 위치·컨텍스트·변경 사항을 보여주는 사이드 레일이 붙었다.
- **한계**: 성능 수치는 공개되지 않았다. 갈라진(fork) 세션을 중첩 해제하는 옵션을 달라는 요청이 GitHub 이슈로 올라와 있다. 앱을 업데이트해야 반영된다.

> 🔧 **적용 포인트** — 지금 포트폴리오는 V3 실험용 worktree(`D:\beomseok-portfolio-design-v3`)를 따로 두고 손으로 오가고 있다. '저장된 환경'에 본 저장소와 V3 worktree를 묶어두면 세션을 열 때마다 경로를 고를 필요가 없다. 도슨트 RAG 튜닝처럼 메인 작업을 하다가 생긴 "이 GSAP 옵션 뭐였지" 같은 질문은 /btw로 빼면 메인 세션 컨텍스트가 덜 오염된다.

### Opus 5.5 패스트 모드 정식 출시 — 대기 명단·베타 헤더 없이 최대 2.5배 빠르게, 대신 표준가의 2배이고 표준 속도로 폴백하면 프롬프트 캐시가 깨진다

10월 15일 Claude Platform 릴리스 노트에 Opus 5.5 패스트 모드의 연구 프리뷰 종료가 올라왔다. ai_freaks.kr의 10월 3주차 소식에도 이번 주 핵심으로 꼽혔다.

- **무엇이 바뀌었나**: 접근 신청과 대기 명단이 없어졌고, 베타 헤더도 더는 필요 없다. 예전 `fast-mode-2026-02-01` 헤더를 보내는 요청도 계속 동작한다. Start·Build·Scale 사용 티어에 패스트 모드 기본 속도 제한이 생겼다. Evaluation 티어는 빠진다.
- **속도와 가격**: 같은 Opus 5.5를 더 빠른 추론 인프라에서 돌린다. 출력 속도가 최대 2.5배이고, 첫 토큰까지 걸리는 시간이 줄어드는 건 아니다. 그래서 짧은 단발 요청보다 긴 스트리밍 응답에서 체감된다. 가격은 입력 100만 토큰당 8달러, 출력 40달러로 표준(입력 4달러)의 두 배다.
- **함정 — 폴백과 캐시**: 패스트 한도는 표준 Opus 한도와 따로 잡힌다. 넘으면 429와 retry-after 헤더가 온다. 문제는 패스트에서 표준으로 폴백하면 두 속도가 캐시된 프리픽스를 공유하지 않아 프롬프트 캐시가 깨진다는 점이다. 그래서 앤트로픽 예제 코드는 패스트 요청의 재시도를 0으로 둔다. SDK 기본값인 2회 재시도 대신 곧바로 실패하고 표준으로 넘어가게 하는 것이다.
- **쓸 수 없는 곳**: Batch API, Priority Tier 약정, AWS의 Claude Platform에서는 안 된다. Microsoft Foundry는 Azure 호스팅 배포에서만 된다. Opus 5·4.8의 패스트 모드는 여전히 프리뷰라 베타 헤더가 필요하다. Claude Code의 패스트 모드는 바뀐 게 없고 추가 사용량 크레딧을 쓴다.

> 🔧 **적용 포인트** — 도슨트 채팅처럼 스트리밍으로 긴 답을 내는 라우트라면 패스트 모드가 체감 속도를 올릴 수 있다. 다만 가격이 두 배이고 TTFB는 그대로라, 지금 `logChat`에 남기는 `llmTtfbMs`만으로는 효과가 안 보인다. 총 생성 시간도 함께 기록해야 한다. 폴백 경로를 만든다면 패스트 시도의 `maxRetries: 0`을 먼저 챙긴다. 그렇지 않으면 재시도 지연에 캐시 미스 비용까지 같이 낸다.

### 앤트로픽 증류 공격 방어 공개 — 증류 업체가 긁어가는 추론 데이터가 90~99% 줄었다는 자체 추정, 정상 사용자도 일부 기능 변경을 감수해야 한다

앤트로픽이 10월 12일 "Strengthening our defenses against distillation attacks"를 냈다. Claude의 응답, 특히 추론 과정을 대량으로 긁어 다른 모델을 학습시키는 증류를 막는 세 갈래 방어다. 다만 보도마다 메커니즘 명칭이 조금씩 다르게 옮겨져 있으니, 세부는 원문을 기준으로 봐야 한다.

- **세 갈래 방어**: ① 8월 31일 이후 만든 새 API 계정은 Claude의 이전 맥락을 편집할 수 없게 했다(Fable 5.1·Opus 5.5 적용). 약하게 보호된 모델을 거쳐 강하게 보호된 모델의 추론을 빼내는 계정 연쇄 수법을 막기 위해서다. Sonnet 5.5는 추론 기록을 요청한 조직만 볼 수 있다. ② 바이오 무기 차단에 쓰던 헌법 분류기(Constitutional Classifier) 방식을 증류 탐지에 적용했다. ③ 반복 증류 계정을 탐지해 차단한다. 수만 개 계정을 막았고, 대부분 두 시간 안에 처리했다고 한다.
- **90~99%의 의미**: 증류 쪽이 가져가는 추론 토큰이 이전의 1/10~1/100로 줄었다는 앤트로픽 자체 초기 추정이다. 독립 검증된 수치가 아니고, 효과가 얼마나 갈지 모른다고 스스로 밝혔다.
- **지목된 곳**: 원문은 Zhipu(GLM-5.3)와 Moonshot(Kimi) 두 곳만 이름을 들었다.
- **정상 사용자 비용**: 앤트로픽은 정상 사용자에게 기능 변경을 요청해야 하고 정상 요청이 잘못 차단될 수 있다는 점을 단점으로 인정했다. 이전에 썼던 추론 요약 방식은 벤치마크 점수를 80.4%에서 71.8%로 떨어뜨렸다는 설명도 덧붙였다.

### Claude가 30분 만에 NIST ECDSA 곡선 시드의 출처를 규명 — 해시가 아니라 1997~98년 Unix 시각으로 시드한 lrand48 난수였다

앤트로픽이 10월 16일 연구 글로 공개했다. NIST P-256 같은 표준 타원곡선의 '시드'는 25년 넘게 어디서 왔는지 설명되지 않아 백도어 의혹의 근거가 돼왔다. 내부 연구용 Claude가 이를 30분이 안 걸려 풀었다.

- **찾아낸 것**: P-192·P-224·P-256·P-384·P-521 시드는 해시 출력이 아니었다. C 라이브러리의 `lrand48` 난수 생성기를 1997년 5월~1998년 4월 사이 Unix 타임스탬프로 시드해 뽑은 값이었다. P-256 시드는 1997년 8월 16일 01:52:34 UTC에 시작한 실행의 1,842번째 후보다. 글에는 이 시드들과 B-233·B-283·B-409·B-571 시드를 그대로 재현하는 코드가 들어 있다.
- **푼 방법**: Claude는 힌트로 주어지던 '농담 섞인 암호문구'를 찾는 대신, 1990년대 소프트웨어가 흔한 약한 난수기를 썼을 거라고 가정했다. 시드 4개의 최상위 비트가 모두 0인 패턴을 보고 `lrand48`(48비트 상태 중 상위 31비트만 반환)의 흔적임을 알아챘다. 비트가 덜 남은 소수 곡선 시드는 격자 축소(LLL)로 생성기 내부 상태를 복원한 뒤, `srand48`이 타임스탬프로 만들 형태까지 되감았다.
- **선을 긋는 부분**: 앤트로픽은 "암호학적 파훼나 새로운 공격, ECDSA 곡선의 약점이 아니다"라고 명시했다. 오히려 누구나 재현할 수 있는 단순한 방식이었다는 점에서 백도어 가능성은 낮아졌다고 본다. 단, 배제한 것은 아니다. B-163 시드, P-224 이상 곡선의 기저점, 그리고 P-256에서 유효했던 876번째 후보를 왜 건너뛰었는지는 여전히 설명되지 않았다.
