## Codex에 작업을 여러 개 맡길 때: 터미널에서는 갈라서 비교하고, 클라우드에서는 환경을 먼저 굳혀 둔다

### Codex 터미널 개편 활용법 — /agents로 병렬 작업 현황 보기, /fork로 맥락은 이어받고 별도 worktree에서 다른 구현 시도

OpenAI Developers가 Codex CLI의 새 터미널 UI를 데모 영상으로 정리했고, swhan0329_가 이를 5개 글로 풀었다. 기능 자체는 9월 23일 0.156부터 10월 2일 0.160까지 여러 버전에 걸쳐 들어왔다. 이번 정리는 이 기능들을 "여러 작업을 맡기고, 살펴보고, 비교하는" 흐름 하나로 묶어 보여준다. 이 중 `/voice`는 [9/21 팁 노트](ai-tips-2026-09-21.md)에서 다뤘다(지금은 기본으로 켜져 있다). 나머지 기능을 쓰임새별로 정리하면 이렇다.

- **`/agents` — 작업 현황 화면**: 작업을 여러 개 맡겼을 때 무엇이 실행 중이고 어디까지 왔는지 한 화면에서 보고, 작업 사이를 오갈 수 있다. 0.160에서는 지난 작업도 "Show more"로 넘겨 볼 수 있게 됐다.
- **`/fork` — 맥락은 그대로, 구현은 따로**: 지금 대화의 맥락을 이어받은 새 세션을 **관리형 worktree**에서 연다. 지금 만든 구현은 그대로 두고 다른 접근을 시도할 때, 배경 설명을 처음부터 다시 할 필요가 줄어든다.
- **전체 화면 UI(`/tui`)**: 상태·힌트·단축키 영역이 따로 생겼다. 코드 변경 내역과 도구 출력은 접어 둘 수 있다. 위로 스크롤하면 터미널 스크롤 버퍼 밖의 이전 대화도 불러오고, 입력창은 아래에 고정된다. swhan0329_는 이것이 화면에서 지난 대화를 찾아보는 기능일 뿐, 모델이 이전 내용을 항상 기억한다는 뜻은 아니라고 짚었다.
- **기타**: `/usage`(사용량 대시보드), `/theme`(테마), Mermaid 다이어그램·LaTeX 수식 렌더링이 추가됐다. 업데이트는 `npm install -g @openai/codex@latest`로 한다.

원문 댓글에는 실사용 경고도 있었다. "작업마다 worktree를 따다 보니 끝난 폴더가 수십 GB씩 쌓여서 치우는 도구를 따로 만들었다"는 것이다. `/fork`를 자주 쓸수록 디스크 정리 습관이 필요하다.

> 🔧 **적용 포인트** — V3 디자인 랩처럼 Codex를 작업자로 쓰는 흐름에 잘 맞는다. 한 시안이 나온 상태에서 `/fork`로 "같은 요구사항, 다른 레이아웃"을 별도 worktree에 뽑게 하고, `/agents`에서 둘의 진행을 같이 보면 된다. 시안 비교가 훨씬 가벼워진다. 다만 이 포트폴리오는 `node_modules`가 커서 worktree마다 설치하면 C 드라이브(240GB SSD)가 금방 찬다. 기존 V3 랩처럼 `node_modules`를 junction으로 연결하거나 worktree 위치를 D 드라이브로 두자. 끝난 worktree는 `git worktree prune`으로 바로 정리하는 습관도 필요하다.

### Codex Cloud 환경 게시 6단계 — 노트북을 닫아도 작업이 이어지게 하는 준비와 체크리스트

[DevDay에서 발표된 Codex 클라우드 환경](ai-news-2026-09-30.md)을 실제로 설정하는 방법이다. 클라우드 실행이나 환경 재사용은 전에도 있었다. 이번에 새로 볼 부분은 대화로 개발 환경을 준비하고, 검토한 뒤 **게시(Publish)해서 다음 작업의 출발점으로 삼는** 흐름이다. 필요한 도구와 실행 조건을 설명하면 Codex가 저장소를 살펴보고 환경을 꾸린다. 설치·테스트 결과를 검토하고 게시하면, 그 파일 시스템이 이후 새 작업의 시작 상태가 된다.

swhan0329_가 정리한 설정 순서(ChatGPT 데스크톱 앱 → 왼쪽 위 메뉴에서 Codex → 새 작업)는 다음과 같다.

1. Work in → **Cloud**
2. Select environment → **Create environment**
3. GitHub 저장소 선택 → Get started
4. 필요한 버전·명령을 설명하고, 설치·테스트 결과를 검토
5. 설정 저장 → **Publish**
6. "Environment published" 확인 → Start a new task

이미 게시한 환경이 있으면 골라서 바로 작업을 맡기면 된다. 환경 관리는 Settings → Codex Cloud → Environments에서 한다. 주의할 점이 있다. 게시된 환경에서 시작한 작업은 **각자 별도의 작업 공간**을 쓰고, 작업 결과가 자동으로 합쳐지지 않는다. 버그 수정·테스트 추가·기능 개선을 따로 맡겼다면 결과도 따로 검토해서 합쳐야 한다. 승인이나 추가 정보 요청이 오면 답해야 작업이 이어진다. 웹·모바일·데스크톱 어디서든 같은 작업을 열어 확인하고 지시를 보낼 수 있다.

노트북을 닫기 전에 확인할 것은 두 가지다.

1. 작업이 정말 **Cloud**에서 시작됐는가 (로컬 작업은 노트북을 닫으면 멈춘다)
2. 필요한 코드와 도구가 그 환경에 준비돼 있는가

> 🔧 **적용 포인트** — 이 포트폴리오로 환경을 만든다면 4단계에서 Node 버전, `npm ci`, `npm run build`, `tests/` 아래 테스트 명령까지 설명해 두고 빌드가 통과하는지 확인한 뒤 게시하자. GLB 모델이나 음성 자산처럼 큰 파일, `.env`에만 있는 키가 필요한 작업(도슨트 RAG·TTS 호출 등)은 클라우드 환경에서 재현되지 않을 수 있다. 처음에는 정적 섹션 수정이나 테스트 추가처럼 외부 키가 필요 없는 작업부터 맡기는 게 현실적이다.
