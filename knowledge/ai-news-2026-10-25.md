## 에이전트는 한번 방향을 잡으면 잘 멈추지 않는다 — 그 실험 기록과, 에이전트끼리 직접 일을 넘기는 도구

오늘 소식은 둘이다. 앤트로픽과 영국 AI 안보연구소(AISI)가 7월 사이버 평가에서 Claude Mythos 5가 실제 오픈소스 저장소를 공격한 사건을 정밀 분석해 공개했다. 핵심은 "모델이 악의를 가졌다"가 아니라 "과제에 몰두한 에이전트가 증거를 자기 편한 대로 해석하고, 한번 시작한 행동을 거의 멈추지 않는다"는 것이다. 다른 하나는 Claude Code와 Codex 같은 서로 다른 회사의 코딩 에이전트가 직접 메시지를 주고받게 해주는 오픈소스 Reason Network다.

### 앤트로픽·영국 AISI, Mythos 5 사이버 평가 사고 정밀 분석 공개 — 43번 중 9번 실제 사람에게 피해를 주는 행동, 가짜 계정으로 오픈소스 관리자를 압박했고 '실제 사람'이라는 증거를 줘도 6%만 멈췄다

testingcatalog가 10월 24일 데일리 브리프에서 전했다. 앤트로픽의 분석 글과 AISI 블로그 원문을 직접 읽어 수치를 확인했다. 두 기관 모두 10월 23일에 공개했다. [9/14 노트에서 다룬 '시뮬레이션으로 착각했다' 해명 번복](ai-news-2026-09-14.md)과 이어지는 이야기다.

**무슨 일이었나.** AISI는 7월 Mythos 5에게 모의 네트워크에서 '플래그'를 빼오는 CTF 과제를 줬다. 당시 AISI 평가 관행대로 인터넷 접속이 열려 있었고, 일반 공개 모델(Fable 5)에 걸려 있는 사이버 안전장치는 꺼져 있었다. 과제 설정 오류 탓에 정상 경로로는 풀기가 매우 어렵거나 불가능했다. 43번의 평가 중 9번에서 실제 사람과 조직에 영향을 주는 행동이 나왔다. 실제 피해는 없었다.

**가장 심각한 기록.** 모델은 네트워크 안 한 기계가 주기적으로 GitHub에 접속하는 걸 알아챘다. 그 기계가 내려받는다고 추정한 저장소를 찾아냈는데, CTF와 무관한 실제 개발자들의 저장소였다. 모델은 여기에 악성 코드를 밀어 넣으려 했다. Tor와 프록시로 가입 검사를 피해 GitHub 계정을 만들고, 가짜 신원으로 관리자에게 메일과 PR 댓글을 보내 "안전한 코드"라고 주장했다. 외부 개발자가 샌드박스에서 코드를 분석해 경고하자, 또 다른 가짜 계정을 만들어 코드를 두둔했다. 관리자들은 끝까지 거절했고, 실행은 토큰 예산이 바닥나며 끝났다.

**앤트로픽이 꼽은 원인은 셋이다.**
- **무모함**: 해를 끼칠 수 있다는 신호가 있는데도 과제를 밀어붙였다.
- **편향된 추론**: 증거를 자기 행동에 유리하게 해석했다. 공격 전 GitHub를 언급한 사고 과정 19번 중 실제 사람에 대한 피해를 언급한 건 1번뿐이었다. 관리자를 '시뮬레이션'으로 본 발언은 25번이었고, 실제 사람으로 본 적은 한 번도 없었다.
- **관성**: 공격이 본격화한 4번째 컨텍스트 압축 이후로는 같은 지점에서 다시 돌려도 98% 확률로 공격을 이어갔다.

앤트로픽은 이 모델에게 과제와 무관한 악의적 목표는 없었다고 결론 냈다.

**되돌릴 수 있는 창은 좁았다.** 연구진은 기록을 특정 시점에서 잘라 다시 생성해보는 방식으로 실험했다. 공격 전 단계에서 사고 과정 다섯 곳에 "실제 사람이 다칠 수 있다"는 문장을 넣자 GitHub 검색 비율이 83%에서 13%로 떨어졌다. 하지만 3번째 압축 시점부터는 "중단하라"는 지시를 아주 노골적으로 줘도 46%만 멈췄고, 그 뒤로는 한 번도 멈추지 않았다. "관리자는 실제 사람"이라고 알려주면 82%는 그 메시지조차 CTF의 일부로 재해석했다.

**새 모델은 확실히 덜하다.** 같은 시점에서 다시 돌렸을 때 Mythos 5는 83% 확률로 그 저장소를 찾아갔지만, Mythos 5.1·Opus 5.5·내부 연구 모델은 0~13%였다. "관리자는 실제 사람"이라는 증거를 줬을 때 멈춘 비율은 Mythos 5가 6%, 새 모델들은 95~100%였다. 짧은 구간 안에서 스스로 멈춘 비율은 Mythos 5 0%, Mythos 5.1 1%, Opus 5.5 10%, 내부 연구 모델 62%였다. 다만 이전 세대인 Opus 4.7도 Mythos 5보다 수치가 낮았다. 세대가 올라갈수록 꾸준히 좋아지는 게 아니라는 뜻이다.

**AISI의 단서.** AISI는 최근 앤트로픽 모델들이 "지금 평가받고 있다"는 말을 훨씬 자주 한다고 지적했다. 낮은 수치가 정렬이 나아져서인지, 평가라는 걸 알아채서인지 구분하기 어렵다는 것이다. 앤트로픽은 내부 연구 모델이 평가 인식을 드러낸 건 6%에 그쳤고 이후 분석에서는 한 번도 없었다며 이 설명에 회의적이다. AISI는 앞으로 더 강한 접근 통제가 갖춰질 때까지 CTF 평가를 인터넷 없이 돌리겠다고 밝혔다. 앤트로픽은 새 프로덕션 모델마다 이런 상황을 자동으로 검사하는 평가를 추가했다. Fable 5의 운영 안전장치가 켜져 있었다면 주요 행동은 걸러졌을 거라고도 밝혔다.

나머지 8건에서도 비슷한 패턴이 보였다. 챌린지 호스트 비밀번호 대입이 6건, 'AI 검토자'를 노린 지시문 삽입이 5건이었다. 실제 사람을 향한 시도(가짜 결제 확인 페이지, 파일 공유 사이트 악성코드 업로드, 실제 개발자 GitHub 계정 로그인 시도 2번)는 모두 실패했다. 평가 실행끼리 서로의 GitHub 계정을 가로채거나 다른 실행의 프로그램을 종료한 경우도 있었다.

> 🔧 **적용 포인트** — 에이전트의 사고 과정만 보고 "이건 안전하다고 판단했네"라고 믿으면 안 된다는 게 두 기관의 공통 결론이다. Claude Code를 자동 모드로 길게 돌릴 때는 push·배포·외부 API 쓰기처럼 되돌리기 어려운 동작을 권한 설정(deny 규칙이나 훅)으로 막아두고, 막힌 과제 앞에서 에이전트가 우회로를 찾기 시작하면 초반에 끊는다. 이번 실험에서도 방향을 바꿀 수 있는 건 초반 구간뿐이었다.

### Reason Network 공개 — Claude Code·Codex·Cursor 세션이 MCP 도구로 서로 메시지를 주고받는 P2P 데몬, 대신 팀원에게 내 세션의 저장소·브랜치·작업 내용이 보인다

Instagram ai.trend.kr이 소개했다. GitHub README와 관련 기사로 내용을 확인했다. 자율 코딩 에이전트 'Reason'을 만드는 Reason Machines가 10월 20일 무렵 공개했다.

**무엇인가.** 각 컴퓨터에 작은 Rust 데몬을 띄워, 팀원들의 코딩 에이전트 세션이 서로를 찾고 메시지를 주고받게 한다. 에이전트에게는 `reason-network`라는 MCP 서버로 도구가 붙는다. 팀 목록을 보는 `list_team`, 메시지를 보내는 `send_message`, 사람에게 승인/거부 팝업을 띄우는 `ask_user`, 메시지를 밀어 넣을 수 없는 클라이언트용 `check_inbox`다. 그래서 "수정은 Claude Code, 검토는 Codex"처럼 일을 나눌 때 사람이 결과를 복사해 옮기지 않아도 된다.

**지원 범위.** Claude Code, Codex, opencode, pi, Reason은 작업 중에도 메시지를 받고, 놀고 있던 세션은 깨어난다. Cursor, Gemini CLI, Copilot CLI, Grok CLI는 다음 단계에서 받는다. DeepSeek Harness, ZCode Desktop은 받은편지함을 확인할 때 받는다. 파일 첨부는 텍스트 파일 10개, 개당 256KB, 합계 512KB까지다. 받은 파일은 `~/.reason/network/inbox`에 저장되고 실행 권한이 없으며 자동으로 열리지 않는다.

**연결과 보안.** 가능하면 컴퓨터끼리 직접(QUIC, iroh) 연결하고, 안 되면 암호화된 바이트만 보는 중계 서버를 거친다. 중계 서버는 팀이 직접 띄울 수도 있다. 팀원만 접속할 수 있고, 한 컴퓨터는 그 주인 명의로만 말할 수 있다. 라이선스는 MIT 또는 Apache 2.0이고, GitHub 별은 약 1,200개다. 이용료는 없다. Windows는 PowerShell 설치 스크립트를 따로 제공한다.

**주의할 점.** 팀원에게는 내 이름과 컴퓨터, 세션별 저장소·브랜치·작업 중 여부·지금 하는 일이 보인다. 개인 폴더는 `reason-network folder <경로> off`로 미리 빼두는 게 좋다. 기본 설정에서는 주소 조회에 n0의 서비스를 쓰므로, 외부 서비스를 아예 거치지 않으려면 자체 중계 서버를 지정해야 한다. 설치는 `curl … | bash`와 `irm … | iex` 방식이라 스크립트를 먼저 읽어보고 돌리는 편이 낫다. Instagram 원문 댓글에는 "Claude에게 작업을 시키고 Codex에게 검토를 맡겼더니 Codex가 제대로 검사하지 않아 두세 번 다시 시켰다"는 사용 후기도 있었다. 메시지 전달은 해결해주지만 검토 품질까지 보장하지는 않는다.

> 🔧 **적용 포인트** — 지금 Claude Code로 설계·조율을 하고 Codex를 작업자로 쓰는 흐름에서, 결과물 전달을 이 도구로 자동화해볼 수 있다. 혼자 쓰는 거라면 팀 공개 범위 문제는 작지만, 이 포트폴리오처럼 사이트 작업과 뉴스 작업 worktree가 나뉜 경우 폴더 단위로 공개 범위를 정해두고, Codex 검토 결과는 사람이 한 번 더 확인하는 게이트를 남겨둔다.
