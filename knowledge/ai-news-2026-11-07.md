## 긴 컨텍스트보다 좋은 메모가 낫다는 측정, 그리고 몇 주 만에 줄어든 RSA-1024의 안전 여유

### 엔비디아 'You don't need long context' — 에이전트가 대화 기록을 버리고 인수인계 메모만 들고 가도 정확도는 거의 그대로, 서버 비용은 3.6~7배 차이

엔비디아 연구진 12명이 11월 3일 arXiv에 'You don't need long context'(2611.05306)를 올렸다. 오래 걸리는 에이전트 작업에서 지금까지의 대화 기록을 끝까지 들고 다녀야 하느냐는 질문을 Claude Opus 4.5와 GPT 5.6 Sol로 코딩·터미널·검색·고객 응대·긴 문서 독해 등 13개 벤치마크에서 시험했다. 비교한 방식은 세 가지다. ① 기록을 전부 쌓기, ② 정해진 길이에 닿으면 인수인계 메모를 쓰고 새 대화에서 과제+메모만 들고 이어가기, ③ 행동 하나마다 메모를 고쳐 쓰고 대화를 버리기.

- **왜 비용인가**: 엔비디아가 H100에 오픈웨이트 모델을 띄워 재 보니, 컨텍스트 창을 25만 6천 토큰으로 연 서버는 1만 6천 토큰 서버보다 같은 토큰을 만드는 데 GLM 5.2는 3.6배, Kimi K2.6은 5.6배, Qwen 3 Coder Next는 7배 비쌌다. API 가격이 컨텍스트 길이와 무관하게 매겨져 사용자가 체감하지 못할 뿐이고, 연구진은 이 절감 폭이 4비트 양자화에 맞먹는다고 봤다.
- **메모 방식(②)**: 한도를 4만 8천→1만 6천 토큰까지 줄여도 정확도는 대부분 기준선 근처였다. SWE-bench Verified에서 Opus 4.5는 70.0%(전체 기록)에서 2만 4천 한도일 때 74.8%로 오히려 올랐고 1만 6천에서도 68.8%였다. 두 모델 모두 22개 설정 중 기준선보다 2점 넘게 떨어진 경우는 5개 이하였다.
- **행동마다 버리기(③)**: 매번 새 직원이 인수인계서 한 장만 읽고 일 하나를 처리하는 구조인데도 SWE-bench Verified 하락은 Opus 4.5 2.0점, GPT 5.6 Sol 3.3점에 그쳤다. 한 번에 다루는 컨텍스트는 중앙값 7천~9천 토큰, 최대도 13만~20만에서 1만 5천~3만 7천 토큰으로 줄었다.
- **긴 문서는 파일로**: 수십만 토큰 문서를 대화에 붙이는 대신 `input01.txt` 같은 파일로 두고 `head`·`sed`로 필요한 줄만 읽게 하자 7개 벤치마크 대부분에서 점수가 올랐다(Opus 4.5 NIAH +40.0점, GPT 5.6 Sol RULER +30.9점). 문서가 수십 배 길어져도 실제로 읽은 분량은 비슷했다.
- **메모에 무엇을 적나**: 작업 '요약'은 모든 사실에 같은 무게를 두고 반복 작업을 과장해 효과가 떨어졌다. 가장 잘 버틴 메모는 ⓐ원래 과제를 거의 그대로 옮긴 문장, ⓑ지금 하는 일·의도·다음 단계, ⓒ쪼갠 계획·완료 조건·관련 파일 위치처럼 이후 작업에 바로 쓰이는 자료의 세 덩어리였다.
- **한계와 숫자 읽는 법**: 압축은 손실이 있다(동전 던지기 결과를 계속 쌓는 과제는 결국 틀린다). 엔비디아의 답은 전체 기록을 파일로 남겨 두고 필요할 때 찾아 읽게 하는 것. 또 '최대 233배' 같은 절감치는 공급사가 짧은 요청에 정가의 20%만 받는다고 가정한 추정이다. 지금처럼 정가가 같으면 SWE-bench Verified(2만 4천 한도)에서 Opus 4.5 비용은 420→296달러로 30% 줄었지만, GPT 5.6 Sol은 메모 작성으로 출력 토큰이 310만→470만 개로 늘어 168→189달러로 13% 늘었다.

연구진은 상태 문장을 받아 행동하고 다시 고쳐 쓰는 것을 처음부터 사후학습한 '의미 상태 공간 모델(SSSM)'까지 제안했다. choi.openai는 Claude Code·Codex도 이미 창이 거의 찼을 때 자동 압축을 하는데, 이 논문은 그 압축을 "훨씬 일찍, 훨씬 자주 해도 된다"는 측정이라 경쟁 축이 창 크기에서 메모 품질로 옮겨 갈 것이라고 정리했다. 2차 보도들도 256K 대비 16K 서버의 토큰당 비용 3.6~7배, 정확도 차이 −3.7~+5.6pp 범위를 같은 내용으로 전했다.

### 구글 딥마인드, AI 에이전트로 구형 RSA-1024의 약점 두 가지 — 서명 위조 이론상 약 1,600배, 키 여러 개 일괄 해독 약 30배 저렴

구글 딥마인드 사이언스팀이 11월 6일 AI 에이전트가 사람 감독 아래 몇 주 만에 1024비트 RSA의 약점 두 가지를 찾았다고 발표했다. UC 샌디에이고·Inria의 나디아 헤닝거, Inria의 에마뉘엘 토메 등 암호 해독 전문가가 함께했고, 딥마인드는 거의 모든 현행 통신이 쓰는 2048비트 이상 키는 여전히 안전하다고 못 박았다.

- **① 서명 위조**: 많은 서명 표준은 서명 전에 정해진 패딩을 붙여 고정 크기 블록을 만든다. 공격자가 서명 장치에 원하는 입력을 넣을 수 있고 블록의 절반 이상을 정할 수 있으면 패딩이 보호 역할을 못 한다. 1024비트에서 64바이트 해시가 딱 그 경계이고, 32바이트 해시에 대해서도 기존 최선보다 이론상 약 1,600배 빠른 알고리즘을 찾았다. 단, 서명 기기를 수십억 번 호출할 수 있어야 한다.
- **재현 실험**: 9월 UC 샌디에이고·Inria 팀이 하드웨어 보안 모듈을 서명 창구로 써서 키를 꺼내지 않고 1024비트 서명을 위조했을 때 CPU 1,380코어년과 다섯 달이 걸렸다. 딥마인드 에이전트는 이미 풀린 키로 같은 공격을 391코어년(CPU 시간 3.5배 절감)에 재현했고, 최대 30만 코어로 3.2일 만에 끝냈다.
- **에이전트가 일한 방식**: 감독 모델 A가 설계·예산·단계별 점검 기준을 정하고 실행 모델 B가 코드 작성·분산 작업·오류 수정을 맡았다. 사람 연구자가 보낸 메시지는 약 20통으로 대부분 "계속해" 같은 승인이었다. 3일 22시간 동안 코드 3만 3,500줄, 분산 실험 336건, 도구 호출 1만 6,292번. 첫 결과가 32비트 정수 오버플로로 틀렸을 때도 처음부터 다시 돌리지 않고 원인을 찾아 고쳤다. 두 모델 이름은 공개되지 않았다.
- **② 같은 크기 키 일괄 해독**: 인수분해 한 번 분량을 미리 계산해 두는 조건에서 키당 추가 비용은 1993년 코퍼스미스 이후 33년간 그대로였다. 에이전트들은 '팬 팩토리' 방식으로 1024비트 키 하나를 추가로 깨는 비용을 약 30배 낮췄다. 한 모델이 증명을 쓰고 다른 모델이 검증했으며 핵심 계산은 Lean 4로 기계 검증했다. 다만 아직 이론 추정이고 실제 구현은 없다.

choi.openai는 7월 Claude Mythos Preview의 HAWK 공격, 9월 Cognition 엔지니어의 RSA-260 인수분해에 이어 공격 비용이 내려가는 속도가 "몇 년 단위에서 몇 주 단위"로 바뀐 게 핵심이라고 짚었다. 9월 UC 샌디에이고·Inria 팀은 서명 창구에 접근 가능한 공격 모델에서는 4096비트 RSA도 128비트 보안에 못 미친다며 양자내성암호로 옮기는 김에 RSA를 떠나라고 권했고, 구글은 PQC 전환 시한을 2029년으로 잡아 둔 상태다. 외신들은 두 논문 모두 아직 동료 심사를 거치지 않았고, 자율 발견이 아니라 사람 전문가와 함께한 AI 보조 연구라는 점을 함께 전했다.

### Reason Machines Aspen — 오픈AI Pando를 참고한 오픈소스 Git 서버, 8코어 한 대에서 한 저장소에 초당 567회 push

[11/3 오픈AI Pando](ai-news-2026-11-03.md)의 후속 격 소식이다. YC 출신 Reason Machines가 코딩 에이전트 수백 개가 같은 저장소에 동시에 커밋하는 상황을 겨냥한 오픈소스 Git 서버 **Aspen**을 공개했다. 블로그 제목은 'Aspen: scaling agentic commits beyond what Git was built for'.

- **설계**: 오픈AI 내부 Git 시스템 Pando의 설계를 참고해, 기존 Git 서버처럼 저장소 단위로 줄을 세우지 않고 브랜치별로 변경을 처리해 서로 기다리지 않게 했다. 클라이언트 쪽 Git 명령은 그대로 쓴다.
- **수치**: 8코어 서버 한 대에서 같은 저장소에 초당 567회 push를 처리했다고 밝혔다. Cursor Origin이 공개한 수치는 초당 최대 300회 이상이다.
- **상태**: 아직 초기 개발 단계다. 이번 교차 검색에서는 회사 블로그 외 독립 보도나 벤치마크를 찾지 못해 수치는 회사 자체 측정으로 봐야 한다.

같은 흐름에서 전 GitHub CEO 토마스 돔케의 Entire도 에이전트용 분산 Git 네트워크 프리뷰를 내놓는 등 '에이전트용 버전 관리'가 잇달아 나오고 있다. 스레드 댓글에서는 같은 브랜치에 push가 몰릴 때 충돌을 어떻게 처리하는지가 빠져 있다는 질문과, 이 정도면 코드보다 의도(스펙)를 버전 관리해야 하는 것 아니냐는 반응이 나왔다.
