### Claude Code, 로컬 샌드박스 모드 도입 중 — 격리 실행 + strict 모드로 ssh까지 차단

Threads에 따르면 앤트로픽이 Claude Code 데스크톱에 로컬 샌드박스 모드 옵션을 준비 중이다. 켜면 새로 시작하는 세션부터 Claude Code가 실행하는 명령이 격리된 샌드박스 안에서만 돌아가고, 여기에 "strict" 모드를 추가로 켜면 ssh처럼 샌드박스 밖에서만 의미가 있는 명령은 밖으로 빠져나가거나 사용자에게 묻지 않고 아예 차단해버린다. 이 설정은 프로젝트 자체 설정으로 덮어쓰지 않는 한 터미널을 포함해 그 컴퓨터의 모든 Claude Code 세션에 적용된다.

웹서치로 교차 확인한 결과, macOS 데스크톱 앱에는 이미 이와 비슷한 네트워크 샌드박스(`OPERON_SANDBOXED_NETWORK`)가 먼저 적용돼 있었는데, 이 때문에 LAN 상의 SSH·SCP·ping·curl이 전부 "No route to host"로 막히는 회귀 버그가 GitHub 이슈로 다수 보고돼 있다. 워크어라운드는 데스크톱 앱 대신 터미널에서 `claude` CLI로 직접 실행하거나(CLI에는 이 네트워크 샌드박스가 적용되지 않는다), 필요할 때마다 `dangerouslyDisableSandbox: true` 옵션으로 한 번씩 허용하는 것이다.

> 🔧 **적용 포인트** — 이 세션도 Claude Code로 로컬 Next.js 개발 서버·미리보기 브라우저를 다루고 있으니, 데스크톱 앱에서 샌드박스가 기본으로 켜지면 로컬 API 서버나 LAN 리소스 접근이 갑자기 막힐 수 있다는 걸 미리 알아두면 좋다. 갑자기 로컬 네트워크 호출이 실패하기 시작하면 먼저 샌드박스 설정과 CLI/데스크톱 실행 방식부터 의심해볼 것.

### Claude Code Auto Mode, 8월 14일부터 기본값으로 — "인젝션 0%" 발표 뒤에 반박도

Threads에 따르면 앤트로픽의 boris_cherny는 모델 정렬 훈련 + 입력 프로브 + 의도 확인 분류기를 층층이 쌓으면 처음 보는 공격에 대해서도 간접 프롬프트 인젝션 성공률을 거의 0까지 낮출 수 있었다고 밝혔고, 이 결과를 근거로 8월 14일부터 Pro·Max·Team 플랜에서 Auto Mode가 기본값으로 바뀌었다. Auto Mode에서는 도구 실행 결과를 프로브가 스캔해 악성 지시가 섞였는지 확인하고, 에이전트의 행동이 실제 사용자 의도와 일치하는지도 함께 점검한다.

웹서치로 교차 확인한 결과, 앤트로픽이 의뢰한 Trajectory Labs의 독립 평가에서는 사전에 준비된(훈련에 쓰이지 않은) 인젝션 시나리오 72개 전체를 Auto Mode가 막아내 성공률 0%를 기록했다고 공식 블로그에 명시돼 있다. 다만 별도 보안 연구자들의 후속 테스트에서는 특정 공격 체인을 쓸 경우 최대 80%까지 성공률이 나왔다는 반박도 나와, "0%"라는 수치를 액면 그대로 믿기는 이르다는 의견이 있다.

> 🔧 **적용 포인트** — Auto Mode를 켜뒀다고 해서 웹 검색 결과, 이슈·PR 본문, 외부 API 응답처럼 신뢰할 수 없는 콘텐츠를 그대로 실행 지시로 흘려보내도 안전하다고 가정하면 안 된다. 자격 증명·배포·결제(예: 이 세션에서도 다루는 git push, 외부 API 키 사용)처럼 되돌리기 어려운 작업은 Auto Mode 여부와 무관하게 수동 승인 단계를 남겨두는 편이 안전하다.

### 앤트로픽 보리스 체르니, "Claude가 매일 앱을 스스로 유지보수" 슬랙 루틴 실험 공개

Threads에 따르면 boris_cherny가 지난 몇 주간 진행한 실험을 공개했다. `proj-claude-maintains-apps`라는 슬랙 채널 하나를 만들고, 여기서 Claude Tag가 iOS·Android·데스크톱·웹·CLI·Agent SDK 전반에 걸쳐 매일 도는 역할별 루틴 여러 개를 굴리는 방식이다. 대표적으로 Crash fuzzer(시뮬레이터를 조작하며 크래시를 유발한 뒤 근본 원인을 찾아 수정), Dup unifier(비슷하지만 미묘하게 다른 코드 추상화를 스캔해 통합 PR을 올림), Dead-code remover(정적으로 도달 불가능한 코드를 곧장 지우지 않고 로깅을 붙여 하루 지켜본 뒤 "정말 죽은 코드"로 확인되면 삭제), Abstraction police(leaky abstraction 수정)가 있고, 공개된 표에는 이 외에도 Ant-only shipper(잊힌 내부 전용 기능 정리·삭제), Logic simplifier/bugfixer, Useless-test pruner, Shipped-feature inliner, Flaky-test fixer, Abstraction improver까지 총 10여 개 루틴이 정리돼 있다.

웹서치로 원문 X(옛 트위터) 게시물까지 교차 확인한 결과 동일한 내용이었고, 보리스 체르니 본인이 "이게 가능할 수도 있겠다는 초기 신호를 보고 있다"는 신중한 톤으로 아직 정식 도입이 아닌 실험 단계임을 밝히고 있다.

> 🔧 **적용 포인트** — 이 패턴(전담 역할을 가진 에이전트 루틴을 하나씩 만들어 정기적으로 자동 실행)은 포트폴리오 규모에도 축소 적용할 수 있다. 예를 들어 매주 한 번 "미사용 export·죽은 코드 스캔" 루틴, "[`src/components`](src/components) 안에서 비슷한 컴포넌트 중복 탐지" 루틴을 별도 예약 작업(scheduled task)으로 분리해두면, 리팩터링을 몰아서 하는 대신 꾸준히 청소되는 코드베이스를 유지할 수 있다.

### 오픈AI DX 엔지니어의 에이전트 가치 계산법 — Value = Outcome / Cost

Threads에 따르면 swhan0329_가 정리한 오픈AI DX 엔지니어 gabriel.chua_의 설명은, Codex 같은 코딩 에이전트에서 얻는 가치를 "Value = Outcome / Cost"라는 단순한 식으로 표현한다. 여기서 비용(Cost)은 단가 하나가 아니라 "단가 × 토큰 수 × 시도 횟수"에, 실제로 결과를 기다리며 옆에 붙어있던 사람의 시간까지 더한 값이다. 단가가 아무리 싸도 같은 작업을 여러 번 재시도시키면 총비용이 커질 수 있다는 게 핵심 메시지다. 실제 사례로 든 것이 Sol과 Luna 두 모델의 역할을 나눈(Sol은 조사·계획, Luna는 구현) Google Slides 유사 도구 CollabSlides 프로토타입인데, Plus 요금제의 7일 사용량 중 약 18%(조사·계획 2% + 구현·배포·다듬기 16%)만 써서 완성했고, 같은 작업을 표준 API 가격으로 환산하면 21.54달러 상당이었다고 공유했다.

이 항목은 개인 실무 노하우 공유 성격이 강해 별도 언론 보도로 교차 검증하기는 어려운 내용이라, 원문 인용 위주로 정리했다.

> 🔧 **적용 포인트** — 모델·에이전트를 고를 때 "토큰 단가가 싼가"만 볼 게 아니라 "이 작업에서 재시도가 몇 번 필요할지"와 "내가 결과를 기다리며 붙어있는 시간"까지 포함해 총비용을 어림잡는 습관을 들이면, 이 세션에서 Sonnet/Opus나 서브에이전트 중 어떤 걸 쓸지 판단할 때도 그대로 적용할 수 있다. 특히 간단한 작업에 무거운 모델을 재시도 없이 쓰는 것과, 싼 모델로 여러 번 재시도하는 것 중 어느 쪽이 실제로 더 저렴한지는 감이 아니라 이 식으로 한 번씩 검산해볼 만하다.
