## 사람이 아니라 에이전트를 전제로 다시 짜이는 개발 인프라 — 코드 저장소와 멀티 봇 협업

### 커서(Cursor), 에이전트 시대용 깃허브 대항마 'Origin' 베타 공개 — 초당 22.6커밋 처리, GitHub 실시간 동기화 지원

Threads에 따르면 커서(Cursor)가 에디터 안에서 코드 작성부터 저장·관리까지 끝낼 수 있는 깃허브 유사 서비스 'Origin'을 공개했다. 기존 GitHub 저장소를 그대로 동기화할 수 있고, Vercel·Buildkite·Depot 같은 서비스와도 연동되며 현재 베타 단계라는 설명이다.

웹서치로 교차 확인한 결과, Origin은 지난 6월 16일 커서의 자체 컨퍼런스 'Compile'에서 처음 발표된 프로젝트로, 인간이 아니라 AI 에이전트가 대부분의 커밋을 만드는 시대를 전제로 설계된 "에이전트 시대의 깃 포지(git forge)"다. 실제 데모에서는 한 저장소에서 초당 22.6커밋을 처리하는 처리량을 보여줬는데, 이는 사람이 손으로 커밋하던 시절의 GitHub 같은 도구가 애초에 감당하도록 설계되지 않은 수치다. 8월 18일(월)부터 커서 Pro·Teams·Enterprise 유료 플랜에 한해 단계적으로 얼리 베타가 열리기 시작했고(Free 플랜 제외), Git 호환 클론·fetch·push·pull, 브라우저 기반 코드 탐색·검색, 코멘트·리뷰·체크·충돌·머지가 포함된 PR, 저장소 설정과 브랜치 보호, 공개 REST API를 함께 제공한다. 특히 처음부터 함께 나온 기능이 GitHub 동기화인데, 기존 프로젝트는 GitHub을 여전히 소스 오브 트루스로 유지하면서 저장소를 실시간으로 Origin에 미러링할 수 있다. 커서 측 의도는 프롬프트 → 에이전트 실행 → 코드 변경 → 리뷰 → CI → 머지 → 배포로 이어지는 개발 루프 전체를 에이전트 중심의 단일 환경으로 압축하려는 것이라는 분석이 나온다.

> 🔧 **적용 포인트** — 이 저장소도 Claude Code로 대부분의 변경을 만들고 있어 "에이전트가 대량으로 커밋하는 상황을 전제로 한 git 포지"라는 Origin의 문제의식과 방향이 겹친다. 다만 아직 커서 유료 플랜 전용 베타라 바로 옮길 이유는 없고, 지금처럼 GitHub을 소스 오브 트루스로 유지하면서 에이전트 작업 이력만 별도로 관측하고 싶어질 때 GitHub 동기화 기능을 참고할 만하다.

### 노우스 리서치, 허미스 데스크톱에 '봇 모드' 공개 — 역할별 AI 봇들이 서로 대화하며 협업

Threads에 따르면 노우스 리서치(Nous Research)가 허미스 데스크톱(Hermes Desktop)에 '봇 모드(Bot Mode)'를 정식 출시했다. 개발·리서치·글쓰기처럼 서로 다른 역할을 여러 AI 봇에 나눠 맡기고, 각 봇에 모델·메모리·스킬·역할을 따로 설정해 팀처럼 운영할 수 있다. 봇끼리 대화하고 작업을 위임할 수 있으며, 여러 봇이 함께 참여하는 그룹 채팅과 반복 작업 자동화도 지원한다는 설명이다.

웹서치로 교차 확인한 결과, 봇 모드는 현재 허미스 에이전트의 독립 플러그인 형태로 퍼블릭 베타 공개됐고(GitHub: NousResearch/Hermes-Bot-Mode, 코어 패치 없이 데스크톱 플러그인으로만 동작), 추후 허미스 데스크톱 본체에 통합될 예정이다. 노우스 리서치가 X(옛 트위터)에 올린 발표에 따르면 기존의 "에이전트 프로필"이 이름을 가진 봇들의 로스터로 바뀌며, 각 봇은 고유한 역할·모델·메모리·스킬·프로필 사진을 가지고 어떤 모델이든 쓸 수 있으며 서로 메시지를 주고받을 수 있다. 한 번 만든 전문 봇은 계속 재사용할 수 있다는 점도 강조됐다. 최신 빌드(hermes-agent #87886) 기준으로는 번들로 기본 탑재돼 기본값으로 켜져 있고, Settings → Connections에 등록된 모든 연결에서 가져온 봇까지 아우르는 멀티 소스 로스터를 제공한다. 각 봇은 자신만의 대화창(Bot Chat)과 크론 기반 반복 작업(Routines)을 가지며, 여러 봇을 그룹 채팅에 불러 함께 논의하게 할 수도 있다.

> 🔧 **적용 포인트** — 이 저장소에서 매일 도는 `weekly-ai-news-threads` 같은 반복 작업을 "수집 담당 → 큐레이션 담당 → 교차검증 담당"처럼 역할을 나눈 봇들이 서로 메시지를 주고받는 구조로 상상해볼 수 있다는 점에서 봇 모드의 방향과 닿아 있다. 다만 Claude Code에는 아직 이런 상시 명명된 멀티봇 로스터 기능이 없으므로, 지금은 SKILL.md 안에 역할별 체크리스트와 단계를 명시적으로 적어두는 방식으로 비슷한 효과(반복 판단 기준의 축적)를 흉내 내는 정도가 현실적이다.
