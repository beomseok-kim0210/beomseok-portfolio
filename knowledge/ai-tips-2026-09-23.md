## Opus 5.5 출시일에 나온 "AI에게 맡기는 법"과 "AI가 만든 걸 AI가 검증하게 하는 법"

### 앤트로픽 공식 Opus 5.5 활용 가이드 — 완료조건만 주고 맡기기, "신중히 생각해" 문구는 이제 필요 없다

Threads(choi.openai)에 따르면 앤트로픽이 Claude Opus 5.5 출시와 함께 공식 활용 가이드를 공개했다. 핵심은 Opus 5.5가 이전 Opus보다 긴 작업을 스스로 이어가는 능력이 좋아졌으니, 매 단계를 지시하기보다 완료 조건과 멈출 조건만 정해주고 맡기라는 것이다. 공식 예시는 "결제 엔드포인트를 옛 클라이언트에서 새 클라이언트로 옮길 것 / 모든 엔드포인트가 새 클라이언트를 쓰고 옛 클라이언트가 삭제되고 테스트가 통과하면 완료 / 설명할 수 없는 이유로 테스트가 실패할 때만 멈춰서 물어볼 것"처럼 세 줄로 구성된다. "신중하게 생각해줘", "단계별로 생각해줘" 같은 문구는 이제 지워도 된다. Opus 5.5는 답하기 전 항상 생각하고 생각량도 스스로 조절하기 때문인데, 앤트로픽이 채팅 제품에서 이 문구를 지운 결과 응답이 더 빨리 시작됐고 품질 저하는 뚜렷하지 않았다. 반대로 디자인 요청에는 더 구체적인 지시가 필요하다고 강조하는데, "흔한 느낌은 피해줘" 같은 범용 지시는 대개 한 기본값을 다른 기본값으로 바꿀 뿐이라 크림색 배경, 제목 속 이탤릭 강조, "01/02/03" 섹션 번호, 알약 모양 버튼처럼 빼고 싶은 패턴을 이름으로 나열하는 편이 효과적이다.

긴 작업의 멈춤 기준은 CLAUDE.md에 명시하라고 권한다. 예시 규칙은 "내 입력이 필요 없는 단계는 계속 진행하고 상태 메모는 다음 작업과 같은 메시지에 넣을 것 / 나 없이는 진행할 수 없을 때, 데이터 삭제·강제 푸시·저장소 밖 변경 전에만 멈춰서 물어볼 것"이다. 코드베이스 전체를 훑는 감사·마이그레이션·리뷰는 서비스별로 서브에이전트를 하나씩 배정하고, 메인 세션이 각 서브에이전트 보고의 근거를 검증한 뒤에야 최종 표에 반영하는 방식을 권한다. 긴 작업은 컨텍스트 압축을 거치므로 TASKS.md 같은 체크리스트 파일에 진행 상황을 적어두면 압축 후에도 남는다. 결과 검토도 사람보다 Opus 5.5가 먼저 하게 하라고 권하는데, 한 초기 테스터는 가장 낮은 effort의 Opus 5.5가 가장 높은 effort의 Opus 5보다 버그를 더 많이 잡고 오탐은 더 적었다고 전했다. 리서치·분석 작업에는 "확인하지 못한 내용은 표시하고 어디를 찾아봤는지 적어줘"라는 한 줄을 붙이면 못 찾은 부분도 보고서 안에서 바로 확인할 수 있다. 속도가 필요한 짧은 대화형 작업에는 Opus 5.5와 함께 나온 연구 프리뷰 `/fast` 모드(2.5배 빠르지만 토큰당 비용 더 높음)를 켤 수 있는데, 몇 시간짜리 자율 작업에는 오히려 표준 모드가 비용 대비 효율이 좋다.

> 🔧 **적용 포인트** — 크라임씬 LLM 심문, 도슨트 GNM 파이프라인, 포트폴리오 V3 그레이박스처럼 여러 단계로 나뉜 Claude Code 작업에 이 가이드가 거의 그대로 적용된다. CLAUDE.md에 "Human 게이트 전에는 멈춤" 같은 규칙이 이미 있다면, 여기에 "테스트 실패·삭제·강제 푸시 전에만 멈추고 나머지는 계속 진행" 식으로 구체적 완료/중단 조건을 추가해보면 좋다. T-008A.3처럼 여러 파일에 걸친 전파 작업은 서비스·파일 단위로 서브에이전트를 나누고 근거를 검증한 뒤 합치는 방식을, TASKS.md 체크리스트는 9차까지 이어진 긴 설계 작업의 진행 상황을 컨텍스트 압축 이후에도 잃지 않는 용도로 시도해볼 만하다.

### 보리스 체르니의 Opus 5.5 버그 사냥법 — Lean·TLA+ 정형 검증으로 Claude Agent SDK PR 16개

Threads(boris_cherny)에 따르면 클로드 코드를 이끄는 앤트로픽 엔지니어 보리스 체르니가 Opus 5.5로 Claude Agent SDK를 정형 검증(formal verification) 언어인 Lean으로 검증해봤더니, 짧은 프롬프트 몇 개만으로 버그와 경쟁 조건(race condition)을 고치는 PR 16개가 나왔다고 전했다. 그는 TLA+도 함께 쓰는데, 데이터 흐름·동시성·상태 관리 문제를 찾을 때는 Lean과 TLA+를 조합해서 본다고 밝혔다. 본인은 두 언어를 잘 모르지만 Claude가 둘 다 능숙하게 다뤄서, 코드를 정형으로 모델링하고 사람이 짚어내기 어려운 버그를 찾는 데 이 접근이 매우 유용하다고 설명했다. 별도 게시물에서는 Opus 5.5가 최근 몇 주간 자신의 주력 모델이었다며, Opus 5.5와 Fable 5.1이 각각 HAProxy를 C에서 Rust로 포팅하는 테스트에서 둘 다 테스트를 거의 통과했지만 Opus 5.5가 9.5시간(Fable 12시간)에 51% 낮은 비용으로 끝냈다고 덧붙였다.

> 🔧 **적용 포인트** — 정형 검증 언어까지 배우지 않고도 Claude에게 "이 모듈을 Lean/TLA+로 모델링해서 동시성·상태 불변식을 검증해줘"라고 맡기는 방식은, 도슨트의 GNM 파이프라인이나 크라임씬의 다단 서랍 전파 로직처럼 상태 전이가 복잡해 사람이 놓치기 쉬운 로직을 검증할 때 시도해볼 만한 도구다. 다만 이는 전문 검증 기법이라 우선순위가 낮은 실험 정도로 접근하는 게 적절하다.

### 커서 엔지니어 로렌 탄의 pstack — AI가 만든 결과를 AI가 직접 실행·검증하게 만드는 워크플로우

Instagram(ai.trend.kr)에 따르면 스페이스X 산하로 편입된 코딩 에이전트 커서(Cursor)의 엔지니어 로렌 탄(Lauren Tan, @poteto)이 강연에서 "같은 AI를 쓰는데 누구는 자는 사이 20건을 끝내고 누구는 아침마다 다시 고치는" 차이는 더 좋은 프롬프트가 아니라 "AI가 만든 걸 AI가 직접 실행해보고 확인하게 했는지"였다고 밝혔다. 같은 실수가 반복되면 이를 다음 작업에서 자동으로 걸리는 점검 장치로 만들고, 신뢰가 확인된 일부터 점점 더 많이 맡기는 방식이다. 웹서치로 확인한 The Neuron·daily.dev·folkfox 등의 설명에 따르면 이 접근은 로렌 탄이 만든 커서 플러그인 `pstack`으로 구체화돼 있다. 이전 메타 React Compiler 팀·넷플릭스 테크리드 출신인 그는 커서 합류 5개월 만에 PR 1,000개 이상을 병합했는데, 핵심은 에이전트가 실제로 제품을 실행하고 UI를 조작하고 실행 추적(trace)을 읽어야 한다는 "검증이 병목"이라는 원칙이다. `pstack`은 23개 워크플로우 스킬, 21개 엔지니어링 원칙, 22개 작업 플레이북, 전용 서브에이전트 2개로 구성되며, 중심 명령 `/poteto-mode`가 버그 수정·기능 개발·조사·야간 실행 등 상황에 맞는 플레이북으로 요청을 라우팅하고, 빌드 통과만으로는 증거로 인정하지 않고 런타임 검증을 강제한다.

> 🔧 **적용 포인트** — `pstack`은 커서 전용이지만, 깃허브의 `michael-denyer/pstack-claude`가 Claude Code·Codex·OpenCode 등으로 이식한 버전을 배포하고 있어 그대로 시도해볼 수 있다. "빌드/테스트 통과"를 완료 증거로 삼지 않고 에이전트가 직접 앱을 실행해 UI를 조작하고 로그·트레이스까지 읽어 확인하게 만드는 원칙은, 브라우저 자동화 도구가 이미 연결된 이 환경에서 크라임씬·도슨트 프론트엔드 변경을 검증할 때 특히 잘 들어맞는다. 반복되는 실수를 다음 작업의 자동 점검 항목으로 남기는 습관도 CLAUDE.md 규칙에 누적해나가기 좋은 아이디어다.
