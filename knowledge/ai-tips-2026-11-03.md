## 에이전트가 빨라질수록 '검수'를 코드로 남겨야 한다 — 팀 규칙은 검사로, 디자인은 촬영 리뷰로, 로딩 화면은 실측으로

### FurtherAI의 AI 네이티브 개발팀 전환기 — 코드가 빨라지면 테스트·리뷰·결정 순으로 병목이 옮겨 가고, 팀만 알던 규칙을 Python 검사 21개로 만들어 에이전트가 스스로 고치게 했다

swhan0329_가 FurtherAI CTO 사샹크 곤달라(Sashank Gondala)의 글 'Building an AI-native engineering org'를 6편으로 정리했다. 한 회사의 자체 보고라 원문 인용 위주로 옮긴다. FurtherAI는 보험 업무를 자동화하는 YC 출신 스타트업이다.

- **결과 숫자와 읽는 법**: 1월 이후 엔지니어 한 명이 하루에 머지하는 변경 수가 약 5배가 됐고, 되돌린 변경 비율은 0.5% 미만이다. 다만 '5배'는 하루 머지 건수일 뿐 제품 가치나 조직 생산성이 5배라는 뜻이 아니고, 되돌림 비율도 전체 버그율과는 다른 지표라고 정리자가 짚었다. 고객이 체감하는 제품 변경은 엔지니어당 월 17~30개 → 9월 45개 → 10월 예상 48개였다.
- **1단계 — 코드가 빨라지면 테스트가 막힌다**: 에이전트가 코드와 테스트를 함께 쓰도록 바꿔 '테스트를 포함한 변경' 비율이 15%에서 91%로(커버리지가 아니다), 사람보다 AI 리뷰를 먼저 거치는 비율이 60%에서 99%로 올랐다. CI는 테스트를 병렬로 돌리고 수정한 부분의 영향을 받는 테스트만 실행해, 같은 17분에 처리하는 테스트 수가 20배가 됐다.
- **2단계 — 팀만 알던 규칙을 코드로**: 버그나 리뷰에서 "원래 이렇게 해야 하는데"가 나오면 작은 Python 검사로 만들어 커밋·PR마다 돌리고, 위반하면 빌드를 실패시키면서 **고치는 방법까지 출력**한다. 이런 규칙이 0개에서 21개로 늘었고, 에이전트는 이 출력을 보고 자기 코드를 고친다. 테스트·검사·AI 리뷰를 모두 통과한 저위험 변경은 자동 머지하며, 그 비중이 최대 3분의 1이다.
- **기반 투자 비용**: 여름 내내 테스트와 도구에 상당한 개발 역량을 썼다. 위 숫자는 그 투자 뒤에 나온 것이다.
- **3단계 — 병목은 '무엇을 만들까'로**: 코드는 빨리 나오는데 모든 결정을 PM·디자이너에게 물으면 그 앞에 대기열이 생긴다. 그래서 엔지니어가 고객 문제 파악부터 기획·출시·효과 확인·운영까지 넓게 책임지게 했다. 숙련도 기준도 바꿨다 — 주니어는 에이전트의 오류를 알아차리고, 시니어는 자기 작업을 계획·리뷰하며, 스태프는 모호한 문제의 절충과 성과 지표까지 책임진다. 매니저에게는 코드 리뷰 완료 여부가 아니라 스테이징에서 실제 사용자처럼 기능을 써 보라고 요구한다.
- **가져갈 질문**: "AI가 코드를 두 배 빨리 써 준다면, 그다음 일은 어디에 쌓일까?" — 테스트인지, 리뷰인지, 의사결정인지부터 찾으라는 것이 정리자의 결론이다.

> 🔧 **적용 포인트** — 이 포트폴리오에도 '셰이더 게이트·픽셀 예산·첫 JS 크기'처럼 반복해서 확인하는 규칙이 있다. 이런 규칙을 작은 Node 스크립트(번들 크기 상한, 금지 import, 이미지 용량 상한 등)로 만들어 `npm run check`와 pre-push 훅에 묶고, 실패 메시지에 고치는 방법을 적어 두면 Claude Code가 그 출력만 보고 스스로 수정 루프를 돈다. CLAUDE.md에 글로 적어 둔 규칙보다 훨씬 확실하게 지켜진다.

### Stageshow — X 디자인 책임자의 '가짜 UI' 제작 스킬, 계획 6단계 뒤 결과를 직접 촬영해 프레임 단위로 검수한다

choi.openai가 소개한 것을 제작자 페이지(benji.org/stageshow)에서 확인했다. X의 디자인 책임자 벤지 테일러(Benji Taylor)가 무료로 공개한 에이전트 스킬이다.

- **무엇을 만드나**: 제품 소개용 '가짜 UI(faux UI)' — 히어로 애니메이션, 기능 카드, 휴대폰 화면 시퀀스, 벤토 그리드 같은 정지·애니메이션 데모. 결과물은 **평범한 React 컴포넌트**라 다른 코드처럼 배치·수정할 수 있다. 무대·창·휴대폰 프레임·모션 같은 어려운 부분은 키트가 제공하고, 스킬은 에이전트의 디자인 판단을 안내한다.
- **설치**: `npx skills add benjitaylor/skills --skill stageshow`. Claude Code, Codex, Gemini, Grok Build 등에서 쓸 수 있다고 한다.
- **계획 6단계**: ① 매체(정지/애니메이션, 반복 여부, 배치, 크기) ② 룩(테마, 강조색, 실제 제품의 크롬과 아이콘) ③ 스토리(사용자 흐름을 3~5개 비트로) ④ 예시(가장 가까운 모범 예제에서 출발) ⑤ 화면(진짜 문구 몇 개 + 나머지는 자리 표시 줄) ⑥ 안무(비트 겹치기, 그룹별 시차, 시작 지점으로 돌아오는 루프).
- **7단계 '리허설'이 핵심**: 에이전트가 `film.mjs`로 데모를 촬영해 프레임 컨택트 시트와 측정 리포트를 만들고, `jumps.mjs`로 한 프레임짜리 튀는 움직임을, `layout.mjs`로 글자·컨트롤이 넘치지 않는지를 검사한다. 그다음 모든 프레임을 보고, 휴대폰 폭과 루프 이음매를 확인하고, 모범 예제와 비교한다. Figma·Gmail 화면을 재현한 테스트에서 스킬을 쓴 쪽 결과가 더 좋았다고 한다.
- **독자 반응**: "정지 이미지만 보고 고치면 애니메이션의 어색함을 놓치기 쉽다"며 촬영 검수 단계를 핵심으로 꼽는 댓글이 많았다. 한글은 줄바꿈과 폰트 대체 때문에 영문 데모와 결과가 달라질 수 있으니 같은 장면의 한글 버전도 비교해 봐야 한다는 지적도 있었다.

> 🔧 **적용 포인트** — 포트폴리오 프로젝트 카드나 개인 프로젝트 소개에 들어갈 짧은 제품 데모 애니메이션을 만들 때 그대로 써 볼 만하다. 특히 '촬영 → 튀는 프레임 검사 → 레이아웃 넘침 검사' 루프는 GSAP·framer-motion 애니메이션을 Claude Code로 다듬을 때 스크린샷 한 장으로 판단하던 방식보다 정확하다. 한글 문구로 넣었을 때 줄바꿈이 깨지지 않는지 `layout.mjs` 결과를 꼭 확인할 것.

### Skullet — 샘플 데이터로 실제 컴포넌트를 재서 스켈레톤을 자동으로 만드는 MIT 라이브러리

choi.openai가 소개한 것을 공식 사이트와 GitHub 저장소(lochie/skullet)에서 확인했다.

- **무엇을 해결하나**: 콘텐츠가 로딩되는 동안 보여 줄 회색 뼈대 화면을 컴포넌트마다 따로 디자인하던 일을 없앤다. 샘플 데이터로 실제 컴포넌트를 보이지 않게 렌더링한 뒤 각 요소의 크기와 모양을 재서, 그 모양 그대로 스켈레톤을 그린다.
- **사용법(React)**: `npm i skullet` 후 `skullet/react`의 `Skeleton`으로 감싼다. `data`(불러오는 값)와 `sample`(자리 표시용 샘플 데이터)을 넘기고, 자식 함수가 실제 데이터를 받아 컴포넌트를 렌더링한다. React 외에 Vue·Svelte·바닐라 JS도 지원하고 라이선스는 MIT다.
- **장점**: 스켈레톤이 실제 콘텐츠와 같은 공간을 차지하므로 데이터가 도착할 때 화면이 튀지 않는다(레이아웃 이동 감소). 소개 글에 따르면 데이터가 빨리 준비되면 스켈레톤 없이 바로 보여 주고, 콘텐츠가 나타나는 애니메이션도 설정할 수 있다.
- **주의**: 아직 v0.0.3인 초기 버전이다. 운영 서비스에 넣기 전엔 API 변경 가능성을 감안해야 한다.

> 🔧 **적용 포인트** — 포트폴리오에서 지식 베이스 카드 목록이나 /docent처럼 데이터를 받아 그리는 DOM 구간이 있다면, 수작업 스켈레톤 대신 `Skeleton`에 샘플 데이터를 넘기는 방식으로 레이아웃 이동(CLS)을 줄여 볼 수 있다. 3D 캔버스 로더(현재 1.6s 로더)에는 해당하지 않으니 DOM 쪽 목록·카드에만 시험적으로 적용하는 게 맞다.
