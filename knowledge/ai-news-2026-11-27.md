## 에이전트가 짠 Rust를 운영 트래픽으로 검증한 앤트로픽, GitHub 계정 하나로 CI/CD까지 뚫린 1Password, 노트북에 들어가는 27B 코딩 모델

### 앤트로픽, Messages API를 Python에서 Rust로 — Claude가 코드를 쓰고 운영 트래픽을 정답지로 삼아 요청당 CPU 약 70%·메모리 80% 이상 줄였고, 결론은 '검증이 새 병목'

앤트로픽이 11월 25일 엔지니어링 글 'Migrating our Messages API to Rust'에서, 외부 고객과 Claude Code·Cowork가 모두 거쳐 가는 **Messages API**를 Python에서 Rust로 옮긴 과정을 공개했다. 2023년에 "사실상 요청 전달기"로 만든 Python 서비스였는데, 2024년 초부터 2026년 가을까지 트래픽이 약 **1,800배** 늘면서 요청마다 형식 검사·프롬프트 조립·토큰화·안전 분류기·스트리밍 분해가 붙었고 Python의 객체 생성·GC 비용이 감당하기 어려워졌다.

- **부분 재작성은 실패**: 올해 초 모델 출력 파서만 Rust로 바꿔 Python에서 불렀더니 CPU가 8~10% 줄었지만, 토큰 하나가 Python↔Rust 경계를 세 번씩 넘는 새 부담이 생겼다. 전체 재작성의 셈법을 바꾼 건 Claude였다(2026년 5월 기준 앤트로픽 병합 코드의 80% 이상을 Claude가 작성). Claude가 핵심 요청 경로 첫 버전을 약 일주일 만에 썼고, 9월에 공개 트래픽을 Rust로 넘겼다.
- **결과**: 요청당 CPU 약 **70%↓**, 메모리 **80% 이상↓**, Claude Code 요청의 첫 토큰까지 시간 중앙값 약 **20%↓**. 서비스 운영과 신규 기능 개발을 멈추지 않은 채 옮겼다.
- **테스트 98% 통과 ≠ 동작 일치**: 기존 통합 테스트 약 700개는 Python 프로세스 안에 과금·사용량 제한을 가짜로 띄우는 구조라 그대로 쓸 수 없었고, Claude가 옮긴 테스트를 감사해 보니 **검사 조건이 느슨해진 곳이 100곳 넘게** 나왔다. 4월 Rust 버전은 테스트 약 98%를 통과했지만 실제 운영 입력에서 Python과 바이트까지 같은 프롬프트를 만든 비율은 **24%**였다. 예컨대 Python은 도구 호출 JSON에서 이모지를 이스케이프하고 Rust는 그대로 써서 몇 바이트씩 달랐다. 자주 쓰이는 기능의 버그 하나가 모든 요청의 일치율을 끌어내려 5월 초 **6.5%**까지 떨어졌다가, 수정이 쌓이며 8월 **99.6%**에 도달했다.
- **운영 트래픽을 정답지로**: 요금은 한 번만 세야 하고 모델 출력은 매번 달라지므로, 모델은 한 번만 호출하고 그 출력을 Rust 쪽에 재생해 넣는 섀도 비교를 했다. 개인정보 때문에 요청·응답 본문은 남기지 않고 "어느 단계·몇 번째 조각·첫 차이 바이트 위치·양쪽 길이"만 기록했는데(예: 둘 다 190바이트인데 17번째 바이트부터 다름 → JSON 키 순서 문제), 같은 버그는 같은 위치·길이 차이를 남기므로 이 기록이 **버그 지문**이 되어 수십만 건 불일치가 버그 몇 개로 묶였다.
- **에이전트 운영 루프**: 스크립트가 10~30분마다 지문을 분류하고, 새 종류가 나오면 조율 에이전트가 작업 에이전트를 하나씩 배정하고 Slack 스레드를 열었다. 처음엔 PR→리뷰→스테이징까지 확인에 몇 시간~며칠이 걸려, 두 코드베이스를 모두 담은 클라우드 샌드박스를 줘 **1초 안에** 두 버전의 프롬프트를 비교하게 했다. 고치면 "옛 코드에선 실패, 새 코드에선 통과"하는 테스트도 함께 추가했다.
- **사람의 역할**: 웹 검색 도구 설명을 파일로 복사해 맞춘 수정은 검증은 통과했지만 "어차피 서비스를 불러야 하니 버릴 코드"라며 엔지니어가 닫았다 — 검증기는 출력만 보므로 에이전트는 가장 싼 길을 찾고, 출시할 만한지는 사람이 판단했다. 에이전트는 그 결정과 이유를 메모리에 남겨 이후 같은 버그의 새 지문을 알려진 버그로 연결했고, "Python이 한 그대로 옮긴다" 규칙이 생긴 뒤 추측으로 옮긴 곳 7군데를 더 찾았다. 6월엔 에이전트가 리뷰 코멘트 약 60개를 묶어 **CLAUDE.md 규칙**을 제안했고, Python을 바꾸면 Rust도 함께 바꾸도록 강제하는 병합 검사가 들어갔다.

앤트로픽은 교훈을 **"검증이 새 병목(Verification is the new bottleneck)"**으로 정리했다. 코드 작성 비용이 내려간 지금은 에이전트가 스스로 결과를 확인할 신호를 얼마나 잘 만들어 주느냐가 맡길 수 있는 일의 크기를 정한다는 것이다. 엔지니어의 일도 차이를 직접 쫓기 → 루프 사이에서 수정 리뷰 → 에이전트가 따를 규칙과 검사 작성으로 옮겨 갔다. 10월 Prime Intellect가 Rust 재작성에서 가상 모델로 터미널 화면을 프레임 단위 비교한 것과 같은 계열의 방법이다. Threads 댓글에서도 "테스트 통과만 믿고 넘겼다가 직렬화·엣지 케이스에서 터진다"는 경험담이 붙었다.

> 🔧 **적용 포인트** — 포트폴리오 리팩터링(예: 씬 컴포넌트 분리, 상태 관리 교체)을 Claude Code에 맡길 때 "테스트 통과"보다 **옛 버전과의 출력 비교**를 검증 신호로 주자. 같은 스크롤 위치·같은 시드에서 리팩터 전후 스크린샷(또는 직렬화한 씬 그래프·GSAP 타임라인 값)을 떠서 첫 차이 지점만 기록하게 하면, 에이전트가 스스로 회귀를 좁혀 갈 수 있다.

> 🔧 **적용 포인트** — 에이전트가 옮긴 테스트는 **단언이 느슨해졌는지** 따로 감사시킬 것(앤트로픽도 100곳 넘게 나왔다). 같은 지적을 두 번 하게 되면 그 리뷰 코멘트를 CLAUDE.md 규칙으로 승격시키는 습관도 그대로 가져다 쓸 수 있다.

### 1Password 침해 — 직원의 회사 GitHub 계정에서 시작해 비공개 저장소·CI/CD를 거쳐 백엔드에 악성 코드가 들어갔고, 일부 고객 이름·이메일·초대·복구 링크 토큰이 나갔다(볼트·키는 무사)

1Password가 11월 25일 공지에서 11월 19일부터 조사해 온 보안 사고를 밝혔다. 공격자는 **직원의 회사 GitHub 계정**에 접근한 뒤 비공개 저장소의 소스 코드를 복사했고, **CI/CD 시스템**에 들어가 백엔드 서비스에 악성 코드를 밀어 넣었다. 그 코드가 관리용 고객 데이터를 내려받았다.

- **노출된 것(일부 사용자)**: 이름·이메일, 계정·사용자 ID, 계정 생성·마지막 로그인 시각, 공개 키, SRP 프로토콜 파라미터, 비밀이 아닌 메타데이터, 그리고 이메일로 보낸 **초대·프로비저닝·계정 복구 링크 토큰**. 1Password는 이 토큰이 SSO 로그인이나 이메일로 보내는 6자리 코드가 있어야 쓸 수 있다고 설명했고, 그 코드를 **영숫자 10자리**로 늘렸다.
- **영향 없음**: 볼트 내용과 항목, 볼트를 보호하는 키, 복구 키, 앱·브라우저 확장. 마스터 비밀번호와 Secret Key는 애초에 서버에 저장하지 않는다.
- **조치**: CI/CD에 있던 인프라 비밀 중 노출 가능성이 있는 자격 증명을 모두 교체했고, 사용자는 계정에서 바꿀 것은 없다고 했다. 다만 초대·계정 복구를 사칭한 메일·문자·전화를 조심하라고 안내했다. 근본 원인 분석은 몇 주 안에 내놓겠다고 했다.

choi.openai는 바이낸스 건과 함께 "직원 계정을 통한 해킹이 계속된다"고 짚었다. 비밀번호 관리 회사조차 **개발자 계정 → 저장소 → 파이프라인 → 운영 서버**로 이어지는 경로가 열려 있었다는 점에서, 공급망 보안의 약한 고리가 사람 계정과 CI 권한이라는 걸 다시 보여 준 사례다.

> 🔧 **적용 포인트** — 이 포트폴리오도 GitHub master push가 곧 Vercel 운영 배포다. GitHub 계정 2FA(가능하면 패스키·하드웨어 키), 오래된 Personal Access Token 정리, Vercel·GitHub에 연결된 OAuth 앱·배포 훅 권한 점검을 한 번 해 두자. Vercel 환경 변수(API 키 등)는 Preview/Production 범위를 나누고 필요 이상으로 Preview에 노출하지 않는 게 좋다.

### PrismML Ternary Bonsai 2.5 27B — Qwen3.8 27B를 5.9GB 삼진 가중치로 줄인 Apache 2.0 모델, SWE-bench Verified 60.8→75.6

PrismML이 11월 24일 **Ternary Bonsai 2.5 27B**를 공개했다. 가중치를 -1·0·+1 세 값으로 바꾸는 삼진(ternary) 압축 계열로, 9월에 나온 Bonsai 2 27B와 같은 **5.9GB** 크기(원본 Qwen3.8 27B 대비 약 9분의 1)를 유지하면서 에이전트 코딩 성능을 끌어올렸다.

| 벤치마크 | Bonsai 2.5 | Bonsai 2 | Qwen3.8 27B(원본) |
|---|---|---|---|
| SWE-bench Verified | **75.6** | 60.8 | 80.6 |
| Terminal-Bench 2.1 | 60.1 | 52.8 | 70.8 |
| AppWorld(도구 사용) | 90.5 | 51.2 | 93.2 |
| τ³-Bench(도구 사용) | 73.9 | 69.1 | 72.8 |
| LiveCodeBench v6 | 83.0 | 83.8 | 87.6 |

- 원본과의 격차는 여전히 SWE-bench 5점, Terminal-Bench 10점가량 남아 있고, 수치는 모두 **PrismML 자체 측정**이다(이전 Bonsai 2 때도 외부 검증 전 수치라는 지적이 있었다).
- NVIDIA·Intel GPU는 llama.cpp, Mac·iPhone·iPad는 MLX로 돌린다. 회사 발표 기준 H100 한 장에서 MTP를 켜면 초당 291토큰 생성, RTX 4090에서 초당 204토큰. 라이선스는 Apache 2.0.
- Threads 댓글에선 "일상에서 중요한 건 도구 호출 점수이고, 5.9GB면 코드가 내 노트북 밖으로 나가지 않는다는 게 클라우드 모델과의 진짜 트레이드오프"라는 반응과 "그래도 저사양 GPU에선 어렵지 않냐"는 반응이 함께 달렸다.

> 🔧 **적용 포인트** — 6GB 안팎이면 일반 노트북 GPU·Apple Silicon에서도 로컬 코딩 보조로 시험해 볼 만하다. 오프라인에서 돌아가는 간단한 코드 설명·리팩터 제안용으로 Ollama/llama.cpp에 올려 Claude Code 결과와 비교해 보되, 원본 대비 격차가 있는 만큼 큰 작업을 맡기기보다 보조 용도로 판단하는 게 안전하다.

### GPT-6.2 사용량 계산 버그 수정 — Astra는 한도가 40%, Sol은 25% 더 빨리 닳게 바로잡히고 사과로 '적립형 리셋'이 지급된다(TestingCatalog 보도)

TestingCatalog가 11월 26일 데일리 브리프에서, 11월 17일 출시된 GPT-6.2의 **출시 초기 사용량 계산 오류**가 수정됐다고 전했다. 그동안 실제보다 적게 차감되고 있었기 때문에, 수정 이후에는 같은 작업에서 **GPT-6.2 Astra는 약 40%, GPT-6.2 Sol은 약 25%** 더 빨리 한도에 닿는다. 대신 Go·Plus·Pro·Business 플랜에 **적립형(banked) 리셋**이 사과 차원에서 지급된다고 한다. 작성자는 본인도 GPT-6.2 대신 GPT-6.1 Sol을 계속 쓰고 있다고 덧붙였다.

OpenAI 도움말 문서는 적립형 리셋이 쓰거나 만료될 때까지 계정에 보관되고, 쓰면 Work·Codex의 5시간·주간 한도를 한꺼번에 채우며 주간 리셋 날짜도 바뀐다고 설명한다. 같은 문서는 Astra가 Sol보다 포함된 사용량을 더 빨리 소모할 수 있다고 이미 안내하고 있다. 다만 "40%/25%"라는 구체적인 수치와 버그 수정 사실은 이번 회차에서 OpenAI 공식 공지로 직접 확인하지 못했다. 같은 브리프에는 Shared Chat·Work 사용량 한도가 12월에 Plus·Pro·Business로 더 넓게 적용된다는 소식도 있었다.

> 🔧 **적용 포인트** — Codex를 워커로 쓰는 작업(GPT-6.1 Sol 사용 중)이라면 지금 바로 바꿀 건 없지만, GPT-6.2로 올릴 때는 지난주 체감 소모량이 아니라 **수정 후 기준**으로 한도를 다시 가늠해야 한다. 적립형 리셋은 긴 작업 직전까지 아껴 두는 편이 낫다.
