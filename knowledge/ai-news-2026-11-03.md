## 에이전트 속도에 맞춰 인프라가 다시 깔리고 있다 — 대화 전송, Git 서버, 그리고 벤치마크까지

### Claude Messages API 'Message threads' 공개 베타 — 다음 턴엔 새 메시지와 직전 응답 ID만 보내고, 토큰은 그대로지만 50만~100만 토큰 요청의 첫 토큰 시간이 약 35% 줄었다

choi.openai가 소개한 앤트로픽 블로그 글과 공식 문서를 직접 확인했다.

- **무엇이 바뀌었나**: 지금까지 Messages API는 매 턴마다 전체 대화 기록을 다시 보내야 했다. 이제 첫 요청에 `"thread": {"type": "create"}`를 붙이면 서버가 대화(답변 포함)를 응답 `id` 아래 보관하고, 다음 요청부터는 새 메시지만 담아 `"thread": {"type": "continue", "previous_message_id": "<직전 응답 id>"}`로 이어 간다. 베타 헤더는 `message-threads-2026-08-12`이고, SDK의 thread 헬퍼가 헤더와 재전송을 대신 처리한다.
- **효과**: 앤트로픽은 Claude Code 사용자 기준으로 50만~100만 토큰 요청의 첫 토큰까지 걸리는 시간(TTFT) 중앙값이 약 35% 줄었다고 밝혔다. choi.openai 정리에 따르면 긴 대화의 요청 크기는 약 800KB에서 1.8KB로 줄었다. 대화가 길수록 효과가 크고, Claude Code에서는 대부분의 사용자에게 기본으로 켜져 있다.
- **바뀌지 않는 것**: 모델은 여전히 매 턴 전체 대화를 읽으므로 **토큰 사용량과 요금은 같다**. 줄어드는 건 업로드 크기와 서버의 검증·토큰화 작업, 즉 지연 시간이다. 스레드가 프롬프트 캐싱을 대신해 주지도 않는다 — 캐싱을 원하면 매 요청에 같은 최상위 `cache_control`을 보내야 하고, 스레드 요청의 캐시 브레이크포인트는 최대 4개다.
- **운영상 주의점**:
  - 스레드는 마지막 요청 후 **5분이면 만료**되고(최대 1시간 안에 삭제), 이어 가기 요청이 404를 받으면 전체 대화를 다시 보내 새 스레드를 만들어야 한다.
  - `system`과 `tools`는 생성 요청에만 보낸다. 이어 가기 요청에 넣으면 `null`이어도 400 오류다. `model`·`thinking`·`tool_choice` 같은 값은 매 요청 같아야 하며, 다르면 `thread_fingerprint_mismatch` 오류가 난다.
  - 메모리에만 암호화해 두고 디스크엔 쓰지 않지만, **ZDR(무보존) 대상은 아니다**.
  - Claude API, Claude Platform on AWS, Google Cloud(앤트로픽 관리형), Microsoft Foundry에서 베타로 쓸 수 있고, Haiku 4.5부터 Fable 5.1까지 지원 모델 폭이 넓다.
- **독자 반응**: "히스토리를 매번 다시 보내던 게 은근 낭비였다, 긴 세션 돌리는 사람에겐 체감이 클 것"이라는 반응과, 결국 서버에 대화를 저장하겠다는 뜻 아니냐는 지적이 함께 달렸다. 무보존이 필요한 서비스라면 후자가 실제로 따져야 할 지점이다.

> 🔧 **적용 포인트** — 포트폴리오의 /docent 음성 도슨트처럼 Claude API로 여러 턴 대화를 이어 가는 기능이 있다면, 대화가 길어질수록 첫 응답이 늦어지는 문제를 줄일 수 있다. 다만 관람객 대화는 몇 분씩 끊기기 쉬우니 5분 만료 뒤 404 → 전체 재전송 경로를 반드시 함께 구현하고(SDK 헬퍼 사용 권장), 짧은 대화 위주라면 효과가 작으니 TTFT를 직접 재 보고 켜는 게 맞다.

### 오픈AI Pando — Codex 부하로 흔들리던 모노레포를 Git 명령은 그대로 둔 채 서버만 갈아 끼워 푸시 지연 약 80% 감소, 하루 1PB 가까이 전송

choi.openai의 6편짜리 스레드를 오픈AI 공식 글 'Scaling Git at OpenAI'와 보도로 교차 확인했다.

- **왜 만들었나**: Codex가 보편화되자 엔지니어 한 명이 여러 변경을 동시에 CI에 올리고, 푸시 하나가 같은 코드를 내려받는 작업 여러 개를 부르면서 부하가 겹겹이 쌓였다. 작년 말부터 가져오기·올리기가 느려지고 병합이 실패해, 하루 병합 성공률이 87%까지 떨어진 날도 있었다.
- **무엇을 바꿨나**: 엔지니어와 에이전트가 쓰는 Git 클라이언트·프로토콜은 그대로 두고 **서버 쪽 백엔드만** 새로 만들었다(Rust).
  - **쓰기**: 저장소 전체를 하나의 순서로 줄 세우지 않고 브랜치별로 따로 처리한다. 서로 다른 브랜치에 대한 푸시는 동시에 반영하고, 같은 브랜치일 때만 순서를 맞춘다. 대신 여러 브랜치를 한꺼번에 보면 각자 시점이 다를 수 있다는 점을 받아들였다.
  - **읽기**: 기존 서버는 요청마다 팩 파일을 새로 압축했지만, Pando는 이미 만든 팩 파일을 여러 요청에 재사용한다. 지역별 캐시 적중률이 99%를 넘는다.
- **숫자**: 푸시 지연 중앙값 약 80% 감소, 병합 성공률은 거의 100%로 안정, CPU 코어 몇 개로 하루 1PB 가까운 Git 데이터를 내보낸다. 한 시간에 57TB를 보낸 적도 있는데 99% 이상이 지역 캐시에서 나갔다.
- **만든 방식**: 착수부터 운영까지 10주. 핵심 구조는 엔지니어 한 명이 설계하고 구현은 Codex 에이전트 팀이 맡았다. GPT-6 Astra 기반 에이전트가 Lean·TLA+로 설계를 형식화해 버그를 찾고 성질을 증명했다고 한다. 소스는 공개하지 않지만 고친 부분 상당수를 Git 프로젝트에 되돌려 기여하고 있다.
- **맥락**: [10/18 앤트로픽 Scion](ai-news-2026-10-18.md) — Claude가 쓰는 코드가 늘며 하루 병합이 3만 건을 넘자 Git을 다른 시스템으로 아예 교체한 사례 — 와 출발점이 같다. 앤트로픽은 시스템을 바꿨고, 오픈AI는 Git 사용법을 지키고 서버만 바꿨다. 일부 보도의 '커밋 2,442% 증가'는 아직 끝나지 않은 4분기 수치와 비교한 회사 발표치라 그대로 받아들이긴 어렵다.

### 세미애널리시스 GDPx — 11개 고부가 분야 8시간짜리 에이전트 과제에서 최고 모델도 12%, 안전 분류기가 순위를 흔든다

choi.openai의 스레드를 세미애널리시스 원문(11월 2일)으로 확인했다.

- **무엇을 재나**: 신모델 발표 때 자주 인용되는 오픈AI GDPval은 필요한 자료를 프롬프트에 다 넣어 주고 문서 하나를 만들게 한다. GDPx는 반대로 **자료를 찾아 맥락을 모으는 과정**까지 시킨다. 예를 들어 금융 과제는 실제 인수 거래를 바탕으로 한 약 2,000개 파일 폴더에서 동료가 하다 만 엑셀을 찾아 마무리해야 한다. 과제당 기본 8시간, 모델별 고유 하네스(없으면 OpenCode)에서 돌리고, 3회 시도 pass@1로 채점한다.
- **분야**: 칩 설계, 사이버보안, 바이오, 금융, 법률, 퀀트 트레이딩, AI 자기개선 연구(RSI), 하드웨어 설계, 소재과학, 정렬, 소프트웨어 엔지니어링 11개. 14개 데이터 파트너가 과제를 만들었다.
- **결과**: 1위 Claude Opus 5.5도 약 12%. 금융·법률은 합격/불합격 채점에서 사실상 모든 모델이 0점이라 부분 점수 평균을 따로 보고했다. choi.openai가 정리한 차트 수치로는 Opus 5.5가 과제당 약 51달러에 12.0%, 미출시 Gemini 4 Carbon이 약 16달러에 10.9%, GPT-6 Astra가 약 54달러에 9.6%였다(원문 본문에는 달러 수치가 없고 차트에만 있다).
- **분야별 강자가 갈린다**: Opus 5.5는 퀀트·하드웨어·칩 설계, Astra는 RSI·소재과학, Carbon은 바이오와 소프트웨어 엔지니어링(근소 차) 1위.
- **안전 분류기 변수**: Opus 5.5와 Astra는 사이버·바이오·정렬 과제에서 안전 분류기가 답을 막아 점수가 깎였다. 이 세 분야를 빼면 둘은 사실상 동점(11.8% 대 11.7%)이 된다. 사이버 분야는 제한이 느슨한 메타 Muse Wonder Full이 큰 차이로 1위였다.

> 🔧 **적용 포인트** — 모델을 고를 때 '종합 1위' 하나보다 내 작업 분야의 점수, 과제당 비용, 그리고 안전 정책 때문에 막히는 영역이 있는지를 따로 봐야 한다는 근거다. 포트폴리오처럼 프런트엔드·3D 위주 작업이라면 소프트웨어 엔지니어링 분야 순위와 비용 곡선을 기준으로, 비싼 모델은 설계·리뷰에만 쓰는 분업을 점검해 볼 만하다.
